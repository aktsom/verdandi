# Windows M5: monome grids (approach note) - version 0.6.0

Written with the code. The owner's grids: a 2023-24 grid 128 (USB CAFE:1110, "USB Serial Device") and a 2011 grid 256 (FTDI 0403:6001, serial M0000163 after trimming FTDI's channel letter). Arcs are supported by the same code (libmonome tells them apart by a size of 0 x 0) but are not owned, so not tested on hardware. Grids are used **directly through their serial ports with libmonome, as the Linux build does; serialosc is not needed** and not used.

## 1. What was there and what was missing
`device_monome.cc` (norns' real grid code over libmonome) was stubbed out on Windows. libmonome has a Windows platform file (SetupAPI serial lookup, overlapped serial I/O at 115200 8N1) with the gaps named in `windows-plan.md` 5.1: the serial is read from the instance id with a pattern that does not fit composite USB devices and cuts hyphens; `monome_event_loop` is not implemented; no hot-plug. And one more found by testing against fake grids: **libmonome's open of a mext device waits for the answer without a time limit** (a port with a monome serial that never answers froze the opening thread for ever).

## 2. Design (platform/windows/grid)
- `grid_core.h` (pure, tested on Linux): the serial from an instance id (`FTDIBUS\VID_0403+PID_6001+M0000163A\0000` gives `M0000163`: FTDI's channel letter is cut; hyphens are kept; a composite function `USB\VID_CAFE&PID_1110&MI_00\...` has none and the **parent** is asked; ids Windows made up are no serial); `monome_like_serial` (`m`/`M` and digits: mext; `m64-`, `m128-`, `m256-`, `mk`, `m40h`, `a40h-`); `classify`: **CAFE:1110 is a grid; 0403:6001 (the generic FTDI id of Arduinos, GPS dongles, lab gear) only with a monome serial or one listed in `monome_serial=`; everything else is not a grid. A port that is not a grid is never opened.** Never by COM number.
- `grid_win.cc`: SetupAPI list of the COM ports (name, vendor and product id, serial from the device or its parents, friendly name) without opening them; the **probe** opens a grid's port for a moment (exclusive: Windows answers "access denied" when another program has it = held), and for the mext family sends the system query with a time limit (`grid_handshake.h`: byte 0x00, three bytes back, twice); the hook `monome_platform_serial_hook` (a 6-line libmonome patch, `windows/patches/libmonome-windows-serial-hook.patch`, applied when CI builds libmonome) gives libmonome the serial the program worked out (a CAFE:1110 without a serial of its own is told `m0`: mext).
- `grid_monitor.cc` (portable, tested with fakes): one scan, diffed against what is listed. A grid is the same grid by **serial**: moved to another USB socket (another COM number) it is removed there and added here at once with the same name and serial (the vport follows name and serial in `grid.lua`, as on Linux). A held port is not handed to the device list and is said in plain words; a grid that is handed over but is not taken (no answer) is tried again every 3 seconds and said once. Triggers: `WM_DEVICECHANGE` (the window of the MIDI layer pokes both monitors) and every 2 seconds. Log lines: `grid: found / removed / skipped ...`.
- `grid_reader.c`: the keys. libmonome has no event loop on Windows and a thread in a Win32 wait cannot be cancelled by `pthread_cancel` (norns cancels a removed device's thread, then joins it): the loop waits 50 ms at a time and checks. Windows' `EV_RXCHAR` fires only for bytes that arrive while it is armed, so every slice also reads. The Linux tests run the same loop against fake grids.
- Everything else is norns' unchanged code: `grid.connect(n)`, `key`, `led`, `all`, `refresh`, `rotation`, `cols`/`rows`, `quads`, the Linux fixes in `grid.lua`/`device_list.cc` (nil-safe removal, handler errors visible, stale pointers).
- **LEDs:** norns sends level maps (`monome_led_level_map`, 16 levels per LED) as on Linux. For the **mext family** (the 128, and the 2011 256 if its serial `M0000163` is mext, which libmonome's pattern table says) that is the protocol's own 16-level command; what the 2011 hardware does with it (quantising to its 4 steps, or not showing levels at all) is the firmware's and **could not be checked here**. A **series** grid (serial `m256-...`) would get on/off plus one global intensity from libmonome. Tilt, rotation, arc rings are libmonome's.
- **All LEDs off** at SYSTEM > RESTART, SLEEP and window close (before the fast exit), and after a crash report (the crash hook already did that on Linux). Not possible: when the process is killed from outside (the launcher's `--exit-after`, Task Manager).
- **SYSTEM > DEVICES > GRID PORTS** (`gridwin.lua`): the grids by name, size, serial and port; problems first (held port: "another program has this port open (serialosc? a serial terminal? another app that talks to the grid?). Close it there; Verdandi opens the grid when the port is free"; no answer: "unplug it and plug it in again"); ports that were left alone with the reason. The DEVICES list itself shows `GRID: n PROBLEM`. The vports are the existing SYSTEM > DEVICES > GRID.
- audio.conf: `monome_serial=` (serials to treat as grids, `;` separated), `monome_ignore=` (COM names or serials to leave alone).

## 3. Small items of this round
- **A. Card rate on the AUDIO page:** when the card's rate differs from norns's the status line shows, in turn with the numbers, `card 44100 Hz, norns 48000 Hz, converted by Windows` (`converted` only in shared mode).
- **B. Main window size and place:** `main-window.conf` in the home folder, saved 600 ms after the last move or resize (not while maximised/minimised/fullscreen), restored at the start; a place that is not on any screen now is not used (the size still is), the size is kept between the window's minimum and the biggest screen. The screen window (F9) keeps its own `screen-window.conf` as before.

## 4. Tests
Linux (all in `run_all.sh`): `grid_core_test.cpp`, `grid_monitor_test.cpp` (two grids, replug on another COM, held port, no answer, generic FTDI never probed), `grid_protocol_test.c` (the **real libmonome** against fake grids on pseudo terminals with the device side of the protocol from `vgrid_proto.c`: sizes, serials `m1234567` and `M0000163`, 16 LED levels reaching the device, key events, all off, the handshake answered and not answered, a serial that is no monome's written with zero bytes, a vanished device ends the reader), `grid_page_windows_test.lua`, `win_state_test.c`. CI: the real norns.exe starts the monitor on the runner (no grid there): the log lines and the table are checked; the libmonome patch is applied and compiled with MinGW. **Not tested without the grids:** the real SetupAPI answers for the CAFE device (composite or not) and the FTDI one, the real overlapped serial I/O of libmonome's Windows layer, key latency, the 2011 hardware's LED steps, hot-plug on a real USB.
