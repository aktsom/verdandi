# M40: the virtual grid: ROTATE, pressing several keys, Windows, the look (investigation and plan; no code yet)

Written before any code. Nothing here is built. The owner decides (section F), then the stages of section E are done one at a time. "Unsure" marks what was not checked.

## A. What there is today

**Linux (and macOS, shared files).** The virtual grid is a pseudo terminal that speaks the device side of the monome serial protocol; libmonome opens it like a USB grid, so matron's monome code and every script see a varibright grid.
- Device: `matron/src/platform/macos/vgrid_device.c` (202 lines; the pty and the link, `vgrid_open(id, cols, rows, ...)`, `vgrid_key(g, x, y, down)`, `vgrid_levels`) and `vgrid_proto.c` (253; the protocol). Header `vgrid_device.h`. The folder name `macos` is historic: the Linux build compiles the same files (`windows/cmake/norns-sources.txt:82-86`, `linux` waf build).
- Window: `matron/src/platform/macos/sdl_bridge.cc:1422-1646` ("virtual grid window"): `grid_pane` (a second SDL window), `grid_held[y][x]` (flags MOUSE and LATCH), `grid_redraw` (1443), `grid_button` (1590) and `grid_motion` (1633), `toggle_grid` (1535, plugs the device in as `virtual grid` through `dev_list_add(DEV_TYPE_MONOME, ...)` and opens the pane). It is opened by the GRID button of the box (`SKIN_GRID`, 3182), F6/the menu entry (`SHELL_MENU_GRID`, 3037) and `toggle_window` (3827); the events of the pane are routed at 4180 (buttons), 4191 (motion), 4205 (close, repaint).
- Look: `vgrid_skin.c` (249 lines), pure cairo: the bead-blasted aluminium plate, light grey square keys, lit keys glowing yellow, an orange outline for a latched key. Sizes `vgrid_sizes[4][2] = {{0,0},{8,8},{16,8},{16,16}}` (line 11), the switch under the plate (`BAR 50`, three buttons of 64 x 26 units, `draw_switch` 190, `vgrid_skin_hit_size` 74). The key grid is hit-tested by `vgrid_skin_hit` (54).
- Sizes and saving: `grid_set_size` (1496) saves the number of keys (64, 128 or 256) in `$HOME/.vgrid-size` (1465-1493; norns.sh sets HOME to the norns home) and plugs the grid out and in again at the new size. Default 128.
- How a click reaches a script: `grid_press` -> `vgrid_key(vgrid, c, r, 1)` -> mext key message on the pty -> libmonome -> `dev_monome_handle_press` (`device_monome.cc:266-281`) -> one `grid_key` event {id, x, y, state} per press and per lift -> `grid.lua` `key(x, y, z)`. Every key is its own event; there is no "chord" event.
- Mouse today: left button = key down while held; dragging across keys plays them one after the other (`grid_motion`: up on the old key, down on the new); **right button or Ctrl+left = latch**: the key stays down (orange outline) until clicked again. So a script can already see several keys held at once, by latching keys one at a time. Not possible today: several keys going down in the same instant, or holding several with the left button.
- Tests today: `macos/tests/vgrid_test.c` (protocol and libmonome end to end), `macos/tests/device_skin_test.c` and `linux/tests/box_c_test.sh:66` (skins), `linux/tests/run_all.sh:120`. Nothing tests the window code of `sdl_bridge.cc` for the grid (clicks, latches, size switch): not found; unsure whether a headless test opens the pane.

**Windows.** Not built, on purpose. `matron/src/platform/windows/vgrid_device_win.c:232-241`: `vgrid_open` logs "the virtual grid: not on Windows (switched off)" and returns NULL unless `VERDANDI_TEST_HOOKS=1` (a fake grid for the CI); the GRID button and F6 only show the toast "VIRTUAL GRID: NOT ON WINDOWS YET" (`sdl_bridge.cc:1555`). `docs/port/phase-m13.md` says the grid and keys were "not wanted now". The owner is right. What is already there: `sdl_bridge.cc`, `vgrid_skin.c` and `vgrid_proto.c` are compiled on Windows (the pane code is shared), and the **virtual arc** already runs on a named pipe (`vgrid_device_win.c`, libmonome patched for pipes, `grid_win.cc` answers the arc's serial), with the generic `open_device(id, cols, rows, rings, ...)` that already takes a grid's size. Missing for a grid: the switch-off, a pipe name and serial for a grid (the arc's are `verdandi-arc-<pid>-m0000002`; `grid_win.cc` serial hook), how the Windows grid monitor (`grid/grid_monitor.cc`, `dev_list_path_listed`) treats a pipe grid (unsure), the saved-settings path (`grid_size_path` uses `$HOME`, or "." when unset: on Windows HOME may not be set, so the file would land in the working folder: unsure, to check), and CI (a window cannot be seen in CI; the fake-grid hook exists, as it does for the arc). Rough size: shared code 0 lines new (the pane is the same), Windows device and monitor glue about 60 to 150 lines, tests and CI about 150 lines; the risk is real grids and the virtual one together (vport order, names), not the code size.

## B. Rotation

**What happens today (measured, not only read).** Rotation is libmonome's: `monome_set_rotation` (`device_monome.cc:129-140`, called by `grid:rotation(n)` through `_norns.grid_set_rotation`, `weaver.cc:2084`, `grid.lua:89`). Verdandi stores nothing about rotation: no saved device rotation exists, a script sets it, it lives in the open device until it is plugged out. I ran the repository's virtual grid through the installed libmonome with rotation 0 to 3 (scratch program, not in the repository):
- 8 x 8: a script LED at (1,0) lights device key (1,0), (0,6), (6,7), (7,1) for rotation 0, 1, 2, 3; a press on device key (1,0) reaches the script as (1,0), (7,1), (6,7), (0,6). LEDs and key events are rotated together, so a script and the device always agree.
- 16 x 8: for rotation 1 and 3 libmonome reports 8 columns by 16 rows to the script (`grid_cols/rows` call `monome_get_cols/rows` live, `device_monome.cc:322-327`, and `Grid:rotation` re-reads them, `grid.lua:91`). Rotation 2 keeps 16 x 8.
- The window draws the DEVICE (key c,r is where key c,r is on the plate), so a script's `g:rotation(1)` shows today as the lit pattern turned on an unturned plate, and a click on a key goes back through the same mapping to the script. For 16 x 16 and 8 x 8 this is clean; the plate stays 16 x 8 for a 16 x 8 device even though the script sees 8 x 16.
- Unsure: how `dev_monome_set_rotation`'s quad offsets (`device_monome.cc:129-137`) behave for a 16 x 16 (256) grid: they change only `quads == 2`; I did not test 256.

**What the window's ROTATE should do (recommended): turn the DEVICE in the window, not the script's view.** The plate is drawn turned by k x 90 degrees clockwise (k = 0..3) and the click position is mapped back to the device key. The device, libmonome and the script do not change: a script sees the same x, y, size and states as before, exactly as when a real grid is turned on a desk. A script that calls `g:rotation(n)` itself keeps working and the two add up (the script turns its picture on the device, the window turns the device). Mapping (cols x rows device, screen grid of rows x cols for odd k): k=0 key (c,r) at screen (c,r); k=1 at (rows-1-r, c); k=2 at (cols-1-c, rows-1-r); k=3 at (r, cols-1-c); hit tests use the inverse. For every size: 64 and 256 are square (the plate keeps its shape); 128 (16 x 8) becomes a tall plate for k=1 and 3 (8 wide, 16 tall), so the window changes shape: the pane is resized (`arrange_windows`, `SDL_SetWindowSize` are in `sdl_bridge.cc`; the device is NOT plugged out). Any size works because only the drawing and the hit test change (the same functions that exist, with one more argument).
- Why not libmonome's rotation for the button: the script would see a 8 x 16 grid (real grids do that too, but every script written for 16 x 8 breaks for it), a script's own `g:rotation(0)` at load would silently undo the owner's choice (or the choice would silently rotate a script that never asked), and a rotation saved by the window would be a hidden state that survives script changes. If the owner wants "the script sees it rotated" it is a second, optional meaning (section F, decision 2).
- Saved: a new line or file next to `.vgrid-size` (`$HOME/.vgrid-rotation`, the number 0 to 3), read when the grid opens, written when ROTATE is pressed. It does not clash with a saved device rotation because there is none. The same note on Windows (the HOME question of section A).
- Button: a fourth switch in the bar (`BAR` is 50 units; four buttons of 64 + 8 gaps = 280 units fit under the 392-unit plate of the smallest grid), label "ROT 0" ... "ROT 270" with the same led as the size switches. No new window, no new page. The bar stays unrotated under the plate (always readable).
- macOS: unchanged. The skin and the pane are shared with the Mac build; the new button and the rotation are behind `NORNS_LINUX_DESKTOP` (which is also set on Windows builds) so the Mac window keeps its three switches.

## C. Pressing several keys with the mouse

Existing modifiers in the grid window: right button or Ctrl = latch. Shift is free in the grid pane (shift is used by the arc window as "4x finer", `sdl_bridge.cc:1837`; Ctrl+Shift+S and Ctrl+Shift+G are keyboard shortcuts of the main window and use Ctrl as well). PIN and the other window shortcuts are keys and do not touch the mouse path of the grid pane. A script sees only single events: `grid.key(x, y, 1)` per key, in the order of the writes (the pty keeps the order; libmonome reads them in order; matron posts one event per key; Lua runs them one after the other, microseconds apart: "simultaneous" means "in one burst").

**Design 1: shift collects, shift release sends (the owner's idea, recommended).** While shift is down, clicking or dragging over keys adds them to a *pending set* (drawn with a marker different from the orange latch: a white outline); a second shift+click on a pending key removes it. Nothing is sent. When shift is released, all pending keys go down in one burst (same order as collected). What happens next must be said plainly, because a real hand lets go: the recommended rule is that the keys then stay held (like latched keys) until the next plain left click anywhere on the grid, which lets them all go in one burst (key-ups in the same order) and is also that click's own press; Esc or closing the window also lets them go. Nothing changes for plain clicks, drags, right-click and Ctrl-click. If the mouse button is still down when shift is released the apply waits for the mouse-up.
- Press: no key-down is sent (only a marker). Release of shift: the burst of key-downs. Next plain click or Esc: the burst of key-ups. A script sees: n key-downs back to back, nothing for a while (it can hold the chord as long as it wants, as with fingers), then n key-ups back to back.
- What can go wrong: a stuck chord (the owner forgets; mitigated: the held chord is drawn with the latch outline and the first plain click frees it; focus loss and closing free it, unplugging the grid frees it by the device going away, `toggle_grid` already clears `grid_held`); focus lost while shift is held (the shift release goes to another window): recommend that focus loss CLEARS the pending set without sending anything (nothing was sent, so nothing can be stuck); the shift key-up must reach the grid pane (SDL key events go to the focused window; the box window shows that F9/F6 work from the grid window, so keys arrive there; unsure whether `SDL_KEYUP` of shift is handled in that path, the stage would poll `SDL_GetModState` on every mouse event and handle `FOCUS_LOST`, as the keys pane does for its typed notes, `sdl_bridge.cc:4224`); touch screens (SDL turns one touch into a left-button mouse, so there is no shift and no second finger: this design does nothing for touch; a "MULTI" switch in the bar would be the touch version, a later option); a double burst order when keys are pending and held at once: latched keys and the old drag are left alone.

**Design 2: shift+drag selects a rectangle.** Dragging with shift draws a rectangle; on mouse-up all keys inside go down together (same hold rule). Simple to explain and to implement (`vgrid_skin_hit` for two corners) and good for "a whole row or block", but it cannot make a chord of scattered keys (a bass note plus a melody key), which is the common case; it can be added on top of Design 1 later (shift+drag = rectangle added to the pending set).

**Design 3: a latch mode (MULTI switch).** A switch in the bar: while ON, every click toggles a key like the existing right-click latch, and turning MULTI OFF lets them all go at once, or "APPLY" sends the downs together. Works with touch and needs no modifier, but it is a mode (easy to leave on by mistake) and mostly repeats what Ctrl+click does today, except the single burst.

**Recommendation: Design 1**, with the keys held until the next plain click. It follows the owner's wording, changes nothing for normal clicks, has no state while shift is up other than the held set (already a concept: the latch), and cannot leave a stuck key through focus loss. Decisions to confirm: what happens to the keys after the apply (held until next click, versus a short tap), and that Esc and focus loss free them.

## D. The look

The norns window's look (SYSTEM > BOX): a style (aluminium, or PIXEL, RETRO, 8-BIT, 16-BIT, `box_style.h`) and five colours (box, keys, encoders, buttons, font; `box_palette.h`). It is chosen in Lua (`lua/core/box_settings.lua`), sent by `sdl_bridge_set_box_look` (`sdl_bridge.cc:748`) as an event and applied in the main thread (`skin_set_look`, `skin_set_pixel_look`, 4097-4110; `device_skin.c:96-122`); the colours are static inside `device_skin.c` (`look_col`), and the pixel shapes are drawn by `box_style.c` as blocks on a 496 x 331 cell image for the norns box only. The grid, arc and keys windows have their own fixed skins (`vgrid_skin.c`, `varc_skin.c`, `vkeys_skin.h`) and do not read the look. The wish list (`docs/port/WISHLIST.md` item 3) says the colours should cover the grid and arc windows; not designed.
- Cheap: pass the five colours (a small accessor in `device_skin.c`) to `vgrid_skin_draw` and tint the aluminium drawing with `box_tint_stop` (`box_palette.h`), the way the box itself does for an aluminium look with other colours: plate = box colour, key caps = keys colour, switches = buttons colour, labels = font colour. About 60 to 100 lines and a redraw on the look event (4097), testable by comparing a rendered image with the default colours (unchanged picture) and one tinted. macOS unchanged (the accessor is behind the Linux guard).
- Expensive: a PIXEL / RETRO / 8-BIT / 16-BIT drawing of the grid (a plate of blocks, hard-edged keys, no anti-aliasing, a new set of shapes and a 16 x 16 key layout in block units, plus tests like `box_style_test.c`). Several hundred lines. Worth doing after the grid itself is settled, if the owner still wants it; the colours alone may already be enough.
- Recommendation: later, as its own stage after rotation and multi-press, colours first.

## E. Stages, tests, risks

1. **ROTATE** (Linux and Windows code, Linux first): `vgrid_skin.c` gets a rotation argument (default 0 = today's picture and hit test), the fourth switch, the pure mapping functions; `sdl_bridge.cc` keeps the rotation, saves it, resizes the pane for odd k; guard `NORNS_LINUX_DESKTOP`. About 150 to 250 lines. Tests (the existing style): a C test of the mapping for all sizes and all four k (every key maps to exactly one screen cell and back, the corner keys, the 16 x 8 turning tall), a hit test on the rotated geometry, a render of the plate for k=0 equal to the old picture, the saved file read and written; the Lua side does not change. CI cannot see the window; the owner's hands: look and feel, window size change, the saved choice after a restart.
2. **Pressing several keys** (design 1): a pure state machine in its own header (like `arc_input.h`, `window_keys`): pending set, apply, release, focus loss, Esc, the order of downs and ups; tested with a table of event sequences; plus an end-to-end check through the real libmonome and the virtual grid (the kind of check made for B above): a burst of downs then ups arrives in order, nothing is stuck after a focus loss, plain clicks and latches behave as before (the existing behaviour is pinned by tests first). About 150 to 250 lines. Owner's hands: whether it is "clean and intuitive", shift handling in his window manager, a stuck key hunt.
3. **Windows parity**: remove the switch-off, a grid pipe name and serial, the monitor check, the settings path, the toast; the shared stages 1 and 2 work on Windows as soon as the grid opens (the guard is set on the Windows build too). CI: the fake-grid hook (`VERDANDI_TEST_HOOKS`) already makes a pipe grid; extend the existing Windows smoke checks to open a grid of each size and check the handshake and a key; the owner's Windows PC for the real thing (real grids together with the virtual one). About 100 to 200 lines plus CI.
4. **Look** (colours first), later.

Order by value and risk: 1, then 2, then 3, then 4; 1 and 2 are shared files, so Windows gets them for free once 3 opens the grid. Alternative: do 3 first so the owner can test everything on both machines as it comes (smallest useful for Windows).

Risks: the shared files with macOS (every change guarded and a Mac-unchanged test of the old picture); the grid pane resize on rotation (window managers, the placement logic `arrange_windows`); a pending set or a held chord stuck after unusual focus changes; Windows real grids plus the virtual one (names, vports); scripts that call `g:rotation` (they keep working, additive); the HOME path of the saved choice on Windows; touch input cannot use shift.

## F. For the owner: the decisions (one at a time; my recommendation first)
1. ROTATE turns the device in the window (scripts see nothing new): **yes** (versus the script seeing a rotated grid, section B).
2. Optionally also a second switch later that sets the script-visible rotation (the same as `g:rotation(n)`): **no, not now**.
3. Multi-press by shift: collect, apply on shift release: **yes**; after the apply the keys stay held until the next plain click (Esc and losing focus free them): **yes**, or a short tap instead?
4. Windows: open the virtual grid there too (with ROTATE and shift multi-press): **yes, after stages 1 and 2**, or first?
5. Look: colours of the box for the grid window first, the pixel looks later: **yes**, not now.
