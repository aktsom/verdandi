# Phase M25 (0.10.14): batch 1 of bringing the Linux port closer to the Windows port

Base: `25f0b79` (the head did not move since the M24 study). The M24 report is in `docs/port/phase-m24.md`. The owner cannot test on the Linux laptop at the moment, so every change here is proven by a test that fails without it (section 8). Items of batch 2 (a dead sclang or scsynth restart, extra sample folders, the AUDIO status line with xrun counts, the rest of the UI parity, a card that comes back) are not touched.

One correction to the M24 study: it said that Quit and the window close finish a tape recording on Linux. That is true for the current code, but the build in the checkout that was used for the study was older than M21; in a fresh build Quit, window close and SLEEP are safe, and RESTART, the shutdown action, SIGTERM, SIGHUP and SIGINT were not (section 1).

## 1. Tape finished when Linux ends (shared C, Linux only in effect)

- **What was wrong.** RESTART and the shutdown action are `pkill -TERM norns` (`system_cmd.cc`). The signal thread of `main.cc` switched the grids off and re-raised the signal, so `matron_cleanup` never ran and the WAV file was cut off (a header that says 0 frames). Ctrl+C or `kill -INT` was worse: after the first line the REPL evaluated, `lua_eval.cc` put the default action back for SIGINT (`signal(SIGINT, SIG_DFL)`), so even the existing LED handler was gone.
- **Change.** `main.cc`, the thread that takes SIGTERM, SIGHUP and SIGINT from the pipe: it calls the same bounded `o_tape_finalize(1500)` the quit path uses (stop, wait up to 1.5 s for the file to be closed), then the grids off (as before), then the signal's own action. The signal handler itself only writes to the pipe, as before. A watchdog thread ends the process by the signal's own action after 4 s whatever hangs. `lua_eval.cc`: the handler that was there before is put back after an evaluation instead of `SIG_DFL` (on a norns device that handler is `SIG_DFL`, so nothing changes there).
- **RESTART and shutdown** still end norns by `pkill -TERM`: that signal path is now complete, so no second way (a quit event from Lua) was added. It would have changed the order of the saves that `norns.restart` and `norns.shutdown` do first.
- **Windows:** the block is inside `#ifndef NORNS_WINDOWS` (Windows ends through `verdandi_win_exit`, M21); `lua_eval.cc` is shared: on Windows `signal()` returns `SIG_DFL` too, so the line does the same as before.
- **Test:** `linux/tests/tape_end_test.sh` (run_all: `audio:a tape recording is closed when norns ends ...`): the real norns records for four seconds, then ends by Ctrl+Q, the window close button, SIGTERM, SIGHUP, SIGINT, `_norns.restart()`, `norns.shutdown()` and the SLEEP page; `windows/ci/wav_check.py` demands a header that matches the file. Before the change: 5 of 8 failed (SIGTERM, SIGHUP, SIGINT, RESTART, shutdown; the header says 0 frames); with only the `main.cc` change SIGINT still failed; after both changes all 8 pass.

## 2. A busy port 5555 or 5556 does not stop Verdandi (Linux; `ws-wrapper` is shared with the Mac)

- **What was wrong.** On a held port the old `ws-wrapper` tried 20 times and crashed with a segmentation fault (nng 1.x crashes when a listener that failed to start is started again). The wrapper starts its child before it binds and only reads the child's output after the bind: with the child (norns) printing, the pipe filled while the port was tried and norns stopped.
- **Change.** `ws-wrapper/src/main.c`: a new socket and listener for every try (the failed one is closed, never started again); the output of the child is read from the first moment; when the port stays busy the wrapper says so in one line and goes on without a console (`WS_WRAPPER_RETRIES` shortens the wait, the address `none` starts it without a console at once); the wrapper ends with the child's exit status; a usage error is a message and status 2. `linux/console-ports.sh` (new): the same rules as the Windows launcher (`console_port.h`): the default port if it is free, else the first free port of default+100 to default+199 (never the other console's port), else off; the holder is found through `/proc` (name and process number), a program that lets go within `NORNS_PORT_WAIT` seconds (default 2: an earlier Verdandi that is still shutting down) is waited for. `linux/norns.sh` chooses once at start, names the holder in its output and, as the Windows launcher does, in the one-line note the norns screen shows (`.verdandi-note`, read by `lua/core/menu.lua`), starts maiden with a copy of its page whose `repl-endpoints.json` names the ports in use, and keeps the choice over a restart of norns.
- **Test:** `linux/tests/console_ports_linux_test.sh` in three parts: the script's choices and lines (part 1), the wrapper with a held port, a chatty child, `none`, a free port and no arguments (part 2), and the real `norns.sh` with sclang and maiden with 5555 held, 5556 held, both held and nothing held: norns starts, sclang's server runs (`Crone.server.serverRunning`), both consoles answer on the new ports (`linux/tests/ws_repl.py`, the handshake of maiden's page), maiden serves `repl-endpoints.json` with the new ports, the plain line is in the launcher output and in `norns.log`, and the holders are still holding their ports. Without the change the wrapper crashed in part 2.
- **Stale Verdandi from an earlier start:** unchanged: a second start raises the window of the running one (it never gets here); a port that an earlier instance is still shutting down is waited for.

## 3. Arc defaults like Windows (shared Lua; shared C one line)

- ARC DRAG: `midimap_settings.lua`. A new setting (no `midimap.conf`) is up/down, as on Windows. A file that has no `arc_drag` line keeps what it meant before (Linux: round the ring, Windows: up/down), a saved line is read as it was. Tests: `midimap_settings_test.lua`, `midimap_page_test.lua`, `probe_arc_drag.lua` (the real arc window with real mouse events: new settings are up/down, a saved circle stays circle).
- Ctrl is the four-times-faster turn on Linux too (`turn_factor` in `sdl_bridge.cc`, the Windows block now `#ifndef __APPLE__`). Checked for clashes: Ctrl+click is the push button (a drag is not started with it, Ctrl held after the press still scales), the arc keys ignore any key pressed with Ctrl, nothing else uses Ctrl with the wheel or a drag in the arc window. The Super key keeps its meaning. Test: the wheel notch in the real arc window with Ctrl held is 8 ticks, without 2.

## 4. The main window's size and place are remembered (shared C)

`sdl_bridge.cc` uses the Windows mechanism (`platform/windows/win_state.c/.h`, pure C, linked into the Linux build through `norns/wscript`): `<home>/main-window.conf`, saved 600 ms after the last change, restored at the next start. A saved place that no screen shows (the unit test `win_state_test.c`: a monitor that is gone, a corner that is hardly on a screen) is not used; the size is kept inside the biggest screen. New on Linux: the temporary move of the window by the grid and arc windows' layout is not saved. Test: `linux/tests/window_state_test.sh` (real window on Xvfb: moved and resized, saved, restored; a place at x 9000, at x -5000 and in a corner; a size above the screen; a damaged file).

## 5. PIN instead of KEYS (shared C, Linux and Windows)

- Removed from the Linux window: the KEYS button (the slot is PIN now, same look as on Windows: lit while on), F7 and `_norns.grid_window("keys")` (they toggle PIN), the right-click item "Virtual keyboard" (it is "Always on top (PIN)"), the MIDI action `keys` (it is `pin`, same place, number 8 of 14), the manual text. A saved mapping with `act.keys.*` lines is dropped with one line in the log (`act.keys.*: the virtual keyboard action is gone ...`), in `midimap.conf` and in the owner's presets; it is not turned into a PIN mapping (Windows reads the old lines as `pin`; there the old action did nothing). Nothing else depends on it: the JACK MIDI source "Verdandi keys" was only made when the keyboard window was open. The source files (`vkeys_skin.c`, `keys_midi.cc`, the keys pane in `sdl_bridge.cc`) stay in the tree because the Mac still uses them; they cannot be reached on Linux and Windows any more. No settings file had a keyboard setting.
- PIN works through `SDL_SetWindowAlwaysOnTop` on every Verdandi window (norns, grid, arc, the detached screen), starts off at every start and is never saved, as on Windows (`pin_state.h`). It needs an X11 session: when SDL's video driver is not `x11` (Wayland) the button does nothing and the box says `ALWAYS ON TOP: NOT AVAILABLE ON WAYLAND`; the log has the plain sentence; the state stays off and the button dark. Not known: how a Wayland desktop's XWayland (an X11 window under Wayland) treats the request.
- Tests: `pin_state_test.c`, `pin_action_test.lua` (Linux, Windows, Mac halves), `probe_window.lua` and `probe_actions.lua` (the real window: F7, the mouse click on the slot and the MIDI note toggle PIN; no keyboard window opens; SDL's flag of every window follows; reports through `_norns.pin_report` with `VERDANDI_TEST_HOOKS=1`), `box_c_test.sh` (the label is PIN on Linux and Windows, KEYS on the Mac; the golden pictures are still proven with the old label through `-DVERDANDI_KEYS_BUTTON`).
