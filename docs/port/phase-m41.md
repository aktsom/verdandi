# M41: the virtual grid: ROTATE and shift multi-press (Linux desktop only)

Stages 1 and 2 of `docs/port/phase-m40-virtual-grid-plan.md`, with the owner's decisions: ROTATE turns the device in the window (scripts see nothing new, no libmonome rotation); multi-press is design 1 (shift collects, shift release sends); Windows and the box look are not part of this. macOS unchanged.

## What was built
- `matron/src/platform/linux/vgrid_view.h` (new, header only, pure C): the mapping of the device to the turned plate and back (`vgv_to_screen`, `vgv_to_device`, `vgv_screen_dims`), the saved rotation (`vgv_parse_rot`, `vgv_load_rot`, `vgv_save_rot`) and the multi-press state machine (`vgv_t`: shift, mouse down, motion, mouse up, Esc, focus lost, rotation changed, device gone; it answers with `vgv_act_t` = hold a key / let it go, and the window does it).
- `matron/src/platform/macos/vgrid_skin.c/.h` (shared with the Mac): `vgrid_geom_t` got `scols, srows, rot`; the plate and the hit test use the drawn plate (`scols x srows`) and map back to the device key; the fourth button ROTATE ("ROT 0", "ROT 90", "ROT 180", "ROT 270", 88 units wide, the led says the device is turned); a white outline for a pending key. `vgrid_skin_units_rot`, `vgrid_skin_geom_rot`.
- `matron/src/platform/macos/sdl_bridge.cc`: the rotation (`grid_rot`, `grid_rotate`), the saved file `$HOME/.vgrid-rotation` (next to `.vgrid-size`, one number 0 to 3; a missing or bad file is 0; an unwritable file says so in the log and the choice lasts until the program ends), the multi-press wiring (mouse, motion, shift key events, Esc, focus lost).
- Behind `VGRID_ROTATE` = `NORNS_LINUX_DESKTOP` and not `NORNS_WINDOWS` (defined in `vgrid_skin.h`): the Mac build compiles none of it, and the Windows virtual grid stays switched off (`vgrid_device_win.c` is untouched). One shared line was changed in a way that is the same on the Mac: the "is the key held" tests in `grid_press`, `grid_let_go` and the latch use `GRID_DOWN_FLAGS` (mouse or latch), because the new pending flag is a flag of the drawing and must not count as held (see "what the headless test found").

## ROTATE
- The plate is drawn turned by k x 90 degrees clockwise: the top left key goes to the top right for 90 degrees. A click is mapped back to the device key, LEDs are drawn where the turned plate has them. Nothing is plugged out: the device, libmonome and the script do not change; a script's own `grid:rotation` still works and adds on top (measured below).
- The pane changes shape when the plate does (the 128 stands up at 90 and 270): the window keeps its top left corner and its scale (the scale is reduced when the new shape does not fit the screen's usable area), is moved back into the screen if needed, and its minimum size follows. It does not scale back up when it turns wide again (a 780 x 478 window that was made 398 x 772 becomes 725 x 444): the window keeps what the screen allowed. The grid is not plugged out and in again (the size switch still does that).
- A size change while turned: the grid is plugged in again at the new size, the rotation stays (it is a variable of the window, not of the device).
- Hover: the grid window has none (no hover state exists in `sdl_bridge.cc`); pressed, latched and pending keys are drawn from the device key through the same mapping.

## Shift multi-press
- Shift down in the grid window: a click or drag over keys adds them to a pending set (white outline), nothing is sent; a second shift click on a pending key takes it out; a drag only adds.
- Shift up: all pending key-downs go out in one burst, in the order they were collected. The keys then stay held like latched keys (orange outline) until the next plain left click anywhere on the grid, Esc in the grid window, or the window closing; the release is one burst in the same order, before the click's own press.
- If the left button is still down when shift is let go, the burst waits for the button (the rest of that drag adds nothing and presses nothing).
- Focus lost while keys are pending: the pending set is thrown away and nothing is sent (the shift key-up may go to another window; nothing was sent, so nothing can be stuck). A held chord stays, as a latched key always did. Rotation changed while keys are pending: the pending set is thrown away without sending (the keys the user meant are not where they were); held keys stay (they are device keys). Window closed or size changed (the device is plugged out and in): everything is forgotten, nothing is sent (the device is gone, the new one starts with no key down).
- Which signal: the shift key events (`SDL_KEYDOWN/UP` of the shift keys reach the grid pane; they are told to the state machine and go on to the old handling) AND the modifier state (`SDL_GetModState`), asked at every mouse click and every mouse motion, so a shift key-up that went to another window is found at the next mouse event. In the headless test the key-up reaches the pane.
- Plain click, plain drag, right-click and Ctrl+click are the old code paths (a Ctrl+shift click is a latch). Shortcuts checked: shift is used by the arc window (4x finer), `Ctrl+Shift+S` and `Ctrl+Shift+G` are keyboard shortcuts of the main window and use Ctrl; no mouse shortcut of the grid pane or the main window uses shift. Esc: in the grid window it is taken only when something is held or pending; otherwise it goes on as before (the right-click menu takes Esc earlier in the event loop, so it still closes the menu).
- Touch screens: SDL turns one touch into a left-button mouse event; there is no shift, so touch does the old plain clicks; nothing was changed for it.

## Measurements (through the real libmonome, `linux/tests/vgrid_rot_e2e_test.c`)
- 8 x 8, 16 x 8, 16 x 16 at each script rotation 0 to 3: every script LED (x, y) lights one device key; the window draws it where the turned plate has it for each of the four turns; a click there finds that device key; the press reaches the script at (x, y). 3 sizes x 4 script rotations x 4 turns, all keys: all agree. For 16 x 8 the script sees 8 x 16 at script rotations 1 and 3 (libmonome; `g:rotation` re-reads rows and columns).
- The quad writes of matron (level maps with the offsets of `device_monome.cc`, swapped for the second quad of a 16 x 8 when turned) light the key a single LED write lights, for every rotation, **also on the 16 x 16** (the quad offsets the plan said were untested: they are right; libmonome turns the map and its offsets itself, so `dev_monome_set_rotation` needs nothing for 4 quads).

## What the headless test found
`linux/tests/probe_vgrid_view.lua` (norns on Xvfb with xdotool: a real mouse and keyboard) found two things: (1) the white pending flag in `grid_held` made the key look held, so the shift-up burst sent no key-down at all (fixed: `GRID_DOWN_FLAGS`); (2) a click on a window that was just created is lost. First taken for the test's setup (no window manager on Xvfb); M43 found the real cause (the size buttons recreated the window under the pressed button) and fixed it: see `docs/port/phase-m43.md`.

## Tests (all in `run_all.sh`; proof of failure on the old code in `phase-m41-without.txt`)
- `linux/tests/vgrid_view_test.c`: the mapping for 4 rotations x 3 sizes (a bijection, the inverse, clockwise, four turns are none), the saved file (0 to 3, spaces, 14 bad texts, missing, unwritable, a long file), the state machine as event tables (collect, drag, remove, apply order, shift up with the button down, a missed shift-up, Esc, focus lost, rotation changed, replug, plain behaviour untouched, 256 keys).
- `linux/tests/vgrid_skin_rot_test.c` (built twice): the Linux build (units, hit test of every key at every rotation and size, the buttons in order with ROTATE fourth, the lit key drawn where the turned plate has it, the white outline, the orange latch outline still orange) and the Mac build (the plate is byte-for-byte the old picture: the hash of the old file's rendering; three buttons, no ROTATE).
- `linux/tests/vgrid_rot_e2e_test.c`: the measurements above plus the multi-press through libmonome (nothing reaches the script while pending, the burst in order, held until Esc, focus lost sends nothing).
- `linux/tests/vgrid_view_guard_test.sh`: the new names are used only inside `VGRID_ROTATE`; the Windows switch-off line is still there.
- The headless window test (`probe_vgrid_view.lua`, `probe_vgrid_view2.lua`, `vgrid_pane_check.sh`, `vgrid_pane_xy.py`): ROTATE through all four positions (the window changes shape, the saved file is 1, 2, 3, 0, 1), a click at the turned place reaches the script at the right key, the size switch while turned keeps the rotation, shift multi-press (nothing before shift up, four key-downs in order after it, Esc lets them go in order, a chord let go by a plain click, keys pending when the focus goes are never sent, a plain drag as before), the next start puts the rotation back, a bad file is 0. The script's grid keys are 1-based: the device key (1,0) is "2,1".
