# Windows M1: first runnable build with null audio (approach note)

Written before the code, as the working agreement asks. Context: `docs/port/windows-plan.md`; M0 passed (run 42689210080). Scope of M1 as decided by the owner: a zip from the Actions run that is unzipped anywhere and started by double-click, no admin rights, nothing to install, unsigned: the norns window with the Verdandi look, matron and Lua booting to the home screen and the SYSTEM menus, sclang and scsynth started in the background **without a sound device**, a script that runs and draws, logs and crash reports in a clear per-user folder, plain on-screen messages when something is missing. **Not in M1:** sound output, grids, MIDI, Link, maiden, installer.

## Findings from M0 that shape the design
1. sclang reads its command line in the ANSI code page: the launcher starts it **from inside its working folder with relative, ASCII-only arguments** (the sclang config file, the class folders are written into a generated file, not passed as arguments).
2. norns's `Crone` class boots a realtime server at sclang start, and **scsynth has no null audio driver** (its Windows audio is PortAudio only): on a machine or runner without an audio device it dies with "Device unavailable". A "no audio device needed" mode is therefore part of M1, and it needs a small change to scsynth itself.

## Design

**1. A null audio driver for scsynth (`windows/patches/scsynth-null-audio.patch`).** A second driver class in `SC_PortAudio.cpp`, chosen when the environment variable `VERDANDI_NULL_AUDIO=1` is set: a thread calls the same engine step as the PortAudio callback every block period with silent input and discards the output. It is a patch of 3.14.1 applied by `windows/ci/build-sc.sh` before configure. It is also the first half of the later realtime work (the driver that is pumped by norns's own callback, M0c/M1 of the plan): same class, other clock. Tried on Linux with a PortAudio build of the same sources, so that "scsynth boots with no device" is proven before CI.

**2. A JACK-compatible null backend inside norns (`matron/src/platform/windows/jack_null/`).** crone (`Client.h`, `Tape.h`) and matron (`jack_client.cpp`) are written against the JACK API (about 40 functions). Instead of rewriting them, Windows gets a small in-process implementation of exactly that API: clients, ports with real buffers, a process callback called by a timer thread at the sample rate (a waitable timer, 48 kHz, 128 frames by default), connections are bookkeeping only, ring buffers, a MIDI port stub. crone's mixer and softcut then run for real, on silence; the AUDIO page and the CPU/xrun counters have values. The same interface is where PortAudio (ASIO/WASAPI) attaches in M2. The shim is portable C and has a **unit test that runs on Linux** (callback cadence, buffers, ring buffer, connect bookkeeping).

**3. Windows platform guard (`NORNS_WINDOWS`).** Windows is built as a desktop build (`NORNS_DESKTOP`, `NORNS_LINUX_DESKTOP` for the shared desktop layer: window, skins, box styles, screen window, toasts) plus `NORNS_WINDOWS` where the Linux desktop parts cannot work. Everything that cannot exist on Windows is **replaced, not ifdef'd into the Linux files where avoidable**: `matron/src/platform/windows/` holds stub implementations (serial/crow, ALSA MIDI, HID, hot-plug monitor, monome devices, the virtual-grid pty, dns_sd/Bonjour, app audio capture, file picker, crash handler, a no-op Link) with **one plain log line each** ("serial devices: not in M1"). Where a shared header names a Linux-only header (`termios.h`, `sys/queue.h`, `alsa/asoundlib.h`, `libevdev`), a small compat header on the Windows include path provides it. Linux and macOS builds do not see these files. Edits to shared files are limited to `#ifdef NORNS_WINDOWS` branches that leave the other platforms byte-for-byte unchanged in behaviour (the Linux tests prove it).

**4. A CMake build for Windows (`windows/cmake/CMakeLists.txt`), built in the msys2 job.** waf is not used on Windows in M1 (one less moving part); the source lists mirror `norns/wscript`. Output: `norns.exe`. Dependencies are the MSYS2 packages that M0 already found (14 of 14), Lua 5.3.6 and libmonome from M0, nng/liblo/SDL2/cairo/sndfile from MSYS2. A cross syntax check on Linux (`windows/ci/xcheck.sh`, mingw-w64) runs over the same files so most compile errors are found before a runner is needed.

**5. The launcher `Verdandi.exe` (`windows/launcher/`, plain Win32 C).** A named mutex (one copy), the per-user folder `%USERPROFILE%\Verdandi` (data) and `%LOCALAPPDATA%\Verdandi\logs` ... decided below, a job object so that the children die with it, starts `scsynth`-free sclang via a generated config from inside its folder with relative arguments, then `norns.exe`; shows plain message boxes for missing pieces (missing file, a second copy, a crash report location). Crash reports: `SetUnhandledExceptionFilter` + DbgHelp minidump in norns.exe and the launcher reports where it is.

**6. The runnable zip.** `Verdandi\` folder: `Verdandi.exe`, `norns.exe`, DLLs, `sc\` (SuperCollider without Qt, from M0), norns Lua and SC sources, resources, fonts, skins. Built by a new `windows-m1.yml` job, with a **headless smoke test on the runner** (SDL dummy video driver, null audio): Verdandi starts, the home screen is drawn and screenshotted, a script runs, sclang and scsynth are up, logs exist, exit is clean; the zip is uploaded. The window and the double-click behaviour are the owner's checklist (`HARDWARE-CHECKLIST.md`).

## What cannot be tested here
Anything on Windows: the MSYS2 build, running `norns.exe`, SDL on Windows, the launcher, DbgHelp. Here: mingw cross **compile checks**, the JACK shim and the scsynth null driver on Linux, shellcheck/actionlint, and the Linux test suite (unchanged behaviour).
