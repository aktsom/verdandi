# Phase M21 (Windows 0.10.12): eight fixes from the audit of 0.10.11

Start: `b0b6d78` (nothing newer on `linux-port`). Exactly the eight findings below; the other audit findings (port 5555, non-ASCII user names, a second SuperCollider, the unbounded wait on the PortAudio worker, sysex, the connect thread, duplicate MIDI names) are untouched. Rule for all of it: nothing may make the sound worse, add delay or need a larger buffer. Every change that is in the sound path (the card's callback) is the same code as before for every buffer that worked before; the new code runs only in the watchdog thread, in the open, and in the program's end.

For each fix: what was wrong, what changed, which test proves it, and that the test fails with the fix taken out (the "without" runs are listed in section 9).

## 1. A card that drops out is tried again, and the chosen device is remembered (`audio_device.c`)
- Wrong: the watchdog reopened once after 2 s; when the card was not listed, Verdandi went to null audio and the retry branch only ran for a clock conflict (`clock_rate != 0`). With another Windows default device, Verdandi moved to it, wrote it as the running output, and never went back.
- Now: `WANT` is the device the user chose (at the start, and when the page applies something that runs); fallbacks never change it. (a) With no sound, the chosen device is tried again every 3 s for every reason; the first failure is one log line, then one line a minute; success is one line. (b) With the sound on another device, every 3 s the backend is asked `present()` (no restart of the host API, no stream touched; an ASIO driver: one load of that driver; a WASAPI device: the list of winmm, which is only plugged-in devices): only when the chosen device is there is the stream closed and the chosen device opened, and "back on '...': it answers again" is said on the page and in the log; a switch back that fails reopens the fallback device and the next look comes later (3 s doubling to a minute): no click every 3 s for a card that is listed but does not open. (c) The page (status line `AWAY`, then the sentence a line at a time) says which device is wanted and which one plays. (d) A different device applied on the page is the wanted device from then on. (e) A card that opens and stops calling back again and again (more than 3 stalls within 40 s of each other) is not reopened in a loop: `give_up`, said on the page, until the next apply.
- Tests: `linux/tests/audio_chain_test.c` scenarios `away_nodefault` (the card gone and nothing else: tried every 3 s, quiet log, back by itself), `away_default` (Windows' default device takes over: the page names both, no close of the running sound while the card is away, back to the card when it answers), `away_apply` (the user chooses another device meanwhile: it stays), and `bigbuf_refused` (the no-loop rule). `linux/tests/audio_page_windows_test.lua` (AWAY and the sentence on the status line).

## 2. A running tape recording is closed on every way of ending
- Wrong: libsndfile writes the WAV header in `sf_close`; only the SLEEP page stopped the tape first. Every other end terminated the process while the file was open: length zero.
- Now: `Tape::Writer::finalize(ms)` (crone): stop, play the fade-out, wait until the disk thread has closed the file; when the audio thread does not finish the fade in a third of the time, the disk thread is told to stop at once (flush and close). It is called from `verdandi_win_exit()` (`exit_win.c`: every Windows way of ending: RESTART and exit code 42, the launcher's restart after a server stop, SLEEP, Quit, window close, the launcher's end event) before the card is stopped, and from `matron_cleanup()` (also Linux/macOS desktop). 1.5 s at most, inside the 3 s exit watchdog; if it does not close in time the log says so (`tape: the recording file could not be closed within 1.5 s: it may be cut off`).
- Tests: `linux/tests/tape_finalize_test.cc` (the real `Tape::Writer`, a child process ending with `_exit`, as `TerminateProcess` does: without finalize the file has no valid header, with it a valid WAV of the right length, also when the audio callback is gone); CI cases `m21-check-tape-{restart,quit,shutdown,launcher}` (the real norns.exe records for 7 s, then is ended in that way; `windows/ci/wav_check.py` checks the header against the file). Not run in CI: the window close button (headless has no window; it goes through the same `matron_cleanup`) and the request file after a server stop (same `_norns.restart`, same exit).

## 3. sclang.exe that ends on its own is noticed (`windows/launcher/verdandi.c`)
- Wrong: only `sclang.log` was watched ("Server 'localhost' exited"); a crash of sclang itself prints nothing and its handle was never waited on.
- Now: the wait loop waits on norns.exe and on sclang's process handle. sclang ending counts like a server stop with its exit code, with the same rule (up to 2 restarts, then one message), and the message and `launcher.log` name sclang itself (`sclang (the SuperCollider language) stopped (error 0xC0000005): restarting it and the script (1 of 2)`; `sclang keeps stopping ...`). An exit code of 0 is logged and not answered (a quit from maiden).
- What the first CI run showed: with the real program, a killed sclang.exe was not noticed at all. The handle the launcher holds is the one of ws-wrapper.exe (it starts sclang as its child and ends with it), and the wrapper did not end (it waited for the websocket's threads and the clients that were still connected: maiden's console connections). Two answers: the wrapper now ends the process at once with the child's exit code (`ws_wrapper_win.c`), and the launcher also looks, every 3 s and from 15 s after the start, for the process `sclang.exe` of its own program folder by name; absent twice in a row it counts as ended ("sclang.exe is not running, though its wrapper has not ended"). The CI report now prints the processes and the end of sclang.log when this check fails.
- Tests: `linux/tests/windows_wine_test.sh` (the real launcher built with mingw under Wine; stand-in norns and sclang; sclang crashes every round: noticed by its process, two restarts with the cause, then the last message and no fourth round); `linux/tests/server_watch_test.c` (the messages); CI `m21-check-sclang-kill` (the real program, `taskkill /F /IM sclang.exe` three times).

## 4. The retry on a clock conflict does not reload every driver
- Wrong: every 3 s `recover()` called `refresh` (Pa_Terminate, Pa_Initialize, a scan that loads every ASIO driver), then `va_probe_one` loaded the chosen one again in the open.
- Now: while the only reason for the retry is the card's rate, the retry asks the one chosen device for its clock (`card_clock`: for an ASIO driver `va_probe_one`, one load of that driver) and goes no further while it is still at another rate than the engine: no restart of PortAudio, no scan, no open, no other driver loaded. A full open (and the `refresh` for a WASAPI device) only when the rate is right or the reason is another. For an ASIO device the recover never restarts PortAudio (an ASIO driver does not come and go like a Windows device). The full scan stays for an explicit request.
- Tests: `audio_chain_test` scenario `clock_quiet` (nine seconds of conflict: no refresh, no open, one ask per retry); Wine test `asio_backend_test` (the clock of the chosen driver is asked with one load: one `create` in the stub driver's log; `present()` also one).

## 5. An ASIO buffer above 2048 frames was silence and a reopen loop
- Wrong: the backend answered a callback above 2048 frames with silence, did not count it as a callback, and the watchdog reopened the card for ever.
- Now: the backend takes callbacks up to 16384 frames; the device layer already runs any number of engine blocks in a callback. The bridge to scsynth holds 16 blocks (12 in flight), so a callback may have at most max(2048, 12 engine blocks) frames: 2048 at the default block of 128 as always, 6144 at a block of 512, 12288 at 1024. A bigger buffer is refused when it is opened, in plain words on the page ("the card's buffer of 4096 frames is more than the engine can follow at a block of 128 frames (at most 2048): choose a smaller BUFFER on SYSTEM > AUDIO, or a larger block= in audio.conf") and is not retried (`give_up`) until the user applies something else. In short: a 4096 or 8192 buffer plays when the engine block is large enough, and says why when it is not; it is never silence and never a loop. The default behaviour (block 128, buffers up to 2048) is unchanged.
- Tests: `audio_chain_test` `reblock4096` (block 512) and `reblock8192` (block 1024): sound at the right pitch, the card opened once; `bigbuf_refused` (4096 at block 128: the sentence, one open in nine seconds, a smaller buffer chosen on the page runs); Wine `asio_backend_test` with the stub driver at 4096 and 8192 (the stub's log shows the peak of the host's output: sound) and 32768 (refused in plain words).

## 6. No ASIO open when the card's rate cannot be read
- Wrong: the guard that keeps Verdandi from asking a driver to change the card's clock only ran when `va_probe_one` worked; otherwise PortAudio's own `ValidateAndSetSampleRate` could call `ASIOSetSampleRate`.
- Now: for ASIO, a rate that cannot be read refuses the open ("the card's rate could not be read (ASIO driver 'X': <the driver's reason>), so Verdandi will not risk changing it"), as busy when the driver refused or did not answer, else as failed; the existing retry and the WASAPI fallback on the same hardware handle it. The driver is retried every 3 s when it is the wanted one (fix 1).
- Where else could Verdandi ask for a clock change? Checked: (a) the probe (`audio_asio_probe.c`) lists `setSampleRate` in its table of functions but never calls it; (b) `Pa_IsFormatSupported` for ASIO only calls `ASIOCanSampleRate`; (c) the only call to `ASIOSetSampleRate` in the program is PortAudio's `ValidateAndSetSampleRate`, reached from `Pa_OpenStream`, and only when the driver's current rate differs from the rate asked, which the guard makes impossible; one window remains that cannot be closed from here: the card's clock changing between the probe and the open (milliseconds); (d) WASAPI exclusive mode sets the device's format, which for a card is its clock: it is a different mode, the user's choice, and tells in the log; shared mode never does. No other path.
- Tests: Wine `asio_backend_test` with the stub driver's control file: rate unreadable (once, then readable: refused, then it opens; and "never works": refused every time) and the stub's log has no `set_rate`.

## 7. APPLY no longer writes the followed rate into audio.conf
- Wrong: after the engine followed the card to 44100, any APPLY wrote `rate=44100` (the running configuration), and later starts in normal mode ran the engine at 44100.
- Now: the configuration the page reads (`vaud_current_config()`, `info.config`) carries the rate that was asked for (`conf_rate`), never the followed one; the page also takes the rate from the file when the file has one; the rate that runs is shown as before (the BUFFER row's milliseconds, the log).
- Tests: `audio_chain_test` `conf_rate` (follow to 44100, apply, the configuration still says 48000, the engine still 44100); `audio_page_windows_test.lua` (followed rate in `info.config` either way, APPLY, audio.conf says 48000; the BUFFER row at 44100 shows 2.9 ms).

## 8. A second copy does not push the logs of the first out
- Wrong: `rotate(logs, "launcher")` ran before the one-copy check; every extra start moved the running copy's `launcher.log` to `.1`, `.2`, `.3`.
- Now: the check is the first thing after the home folder exists; a second copy appends one line to the log of the running one, brings its window forward and ends with code 3. It touches no other log (the other logs rotate only after the check, as before).
- Tests: Wine test (two real launchers: `launcher.1.log` and `.2.log` still the old ones, norns.log rotated once); CI `m21-check-two-copies` (the real program).
