# M42: ext folders are listed together at the top of the file browsers (replaces the by-name placing of M38)

## What happened
M38 sorted each "[ext] <name>" folder into the list by its real name. The owner tried it on Windows (0.10.22 bac1a4f): the ext folders showed together at the top ("[ext] 01 dropbox samples", "[ext] boss rc 500 looper", "[ext] cymatics", then "cc2_live-audio", "dronecaster"), that is in the order of the bytes of the link names, not the M38 order (cymatics after cc2_live-audio). The owner says he prefers them grouped anyway.

## The new rule (one place, both platforms)
All "[ext] <name>" entries are listed together at the top of the folder list, A to Z among themselves by their real name with the rules of SYSTEM > EXT FOLDERS (M33: case ignored, digits first, numbers in number order; `util.natural_less`, a copy of `core/menu/extra.lua`'s function; the test checks that both give one order). The "[ext] " mark stays in the text. Every other entry follows in the order the platform gave it, as before M38. A normal folder with the same name as an ext folder is a normal entry: it stays where the platform put it, both are listed. A listing without an ext folder is returned as it is (the same table).
The code is `util.ext_place` in `lua/lib/util.lua`, called by `util.scandir`, which every browser uses: `fileselect.lua:123` (script browsers, the tape page's pickers, any script's file chooser) and `params/file.lua:81` (the params file picker). Nothing else lists dust/audio for the user. The M38 code that asked `sort` for the platform's order (`util.dir_less`) is gone: the new rule never compares an ext name with a normal name, so no platform order is needed (Linux runs no extra program now). SYSTEM > EXT FOLDERS, the links and their storage are untouched.

## Why Windows did not follow the M38 rule
**Not found by reading, and not reproduced here (there is no Windows in this container).** What was checked:
- Every browser lists through `util.scandir` (grep: no other listing of dust/audio); the Windows branch is `util.ext_place(_norns.listdir(directory))`, the same call as on Linux. The Windows zip of the build the owner ran contains the M38 `util.lua` (checked in the published zip).
- The M38 unit test passed for the Windows listing shape, and the owner's folders put through the same function (a listing in byte order with "[ext] ..." first, the way `_norns.listdir` sorts) give "cc2_live-audio" before "[ext] cymatics" there too. So M38's logic is right for that input; the real listing the program gives must differ from it. Candidates that fit the picture and that I could not tell apart: an ext junction reported without the trailing "/" (then it would not match the folder pattern and would stay where the platform put it), or names in the listing that differ from "[ext] <name>/". 
- To stop guessing the Windows CI now asks the real program: `windows/ci/maiden_probe.py` (the extdrop scenario) makes ext folders "cymatics" and "01 dropbox samples" next to the junction it already has and two normal folders "cc2_live-audio" and "dronecaster", prints what `_norns.listdir` gives (probe line `extsort-raw`) and what `util.scandir` makes of it (`extsort-scan`), and checks the new rule (`extsort-grouped`). The result of the first windows-m1 run on this change is in the report that closes this phase (see STATUS.md).
It was a different code path or a different listing, not a logic error of M38's unit test: M38's tests built the listing by hand, the real one comes from `FindFirstFileW` in `norns_win_listdir` and was never run through the real program in CI.
