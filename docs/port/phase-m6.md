# Windows M6: maiden, installing scripts, tools, serialosc - version 0.7.0

## 1. Maiden
- **What ships:** `maiden\maiden.exe` (the Go server, the same pinned commit and patches as the Linux build: `--host`, the systemd-unit guard) and its built web app `maiden\app\build`, the catalog sources `maiden\dist\sources`. The owner needs no Go, no node. They are built by the CI job **maiden** on a Linux runner (`windows/ci/build-maiden.sh`: the server is pure Go, `GOOS=windows` cross-builds; the web app is static files, built with node 16 downloaded and checked against nodejs.org's checksums, as `linux/maiden-build.sh` does). Checked here: the Go server cross-builds for Windows with the patches; the web build and the Windows run are the CI's and the owner's.
- **Start:** the launcher (`windows/launcher/verdandi.c`) starts `maiden.exe server --host 127.0.0.1 --port 5000 --app app\build --data <home>/dust --doc <app>/doc --config maiden.yaml` next to norns.exe, in the round's job object (it ends with the round), log in `logs\maiden.log`. **Bound to 127.0.0.1 only**: a loopback listener does not ask Windows Firewall. If port 5000 is already used by another program the launcher says so (`maiden: port 5000 is in use ...`) and does not start it (another port: `NORNS_MAIDEN_PORT`). The catalog sources are copied to `dust\data\sources` the first time. `VERDANDI_MAIDEN=1` (set by the launcher when maiden is there) turns on the MAIDEN button of the window: it opens `http://127.0.0.1:5000/maiden` in the default browser (a note if nothing answers).
- **The consoles (item 5):** maiden's norns and sclang consoles are websockets at 5555 and 5556 that put a program's standard input and output on a socket. The Linux `ws-wrapper` forks; the Windows one is `windows/ws-wrapper/ws_wrapper_win.c` (CreateProcess with pipes, nng websocket, the same Origin check: only a page that maiden served may open the consoles; clients without an Origin header, such as maiden-repl, may). The launcher starts **norns.exe and sclang through it** (`ws-wrapper.exe ws://127.0.0.1:5555 norns.exe`; sclang with `-i maiden` instead of `-D`, as on Linux), the wrapper's exit code is the program's (42 = restart still works) and the output still goes to the log. If `ws-wrapper.exe` is missing or `VERDANDI_NO_WRAPPER` is set the programs start directly as before M6. Why the "no console input" line: norns.exe's stdin was closed; now it is the pipe the console writes to. **Not tested without Windows:** that sclang 3.14.1 on Windows reads its stdin from a pipe with `-i maiden` (the CI probe asks it and says), and Windows Firewall behaviour (loopback only: none expected).

## 2. Installing scripts: git and the shell (items 2 and 3)
- **maiden's installer needs no git binary:** it uses go-git (pure Go), with submodules (`RecurseSubmodules`), for git URLs, and downloads zips over HTTP(S). So catalog install, update and delete work from maiden without anything else. Local `file://` zips cannot be used on Windows (Go reads `file:///C:/...` as `/C:/...`); the catalog never does.
- **What scripts themselves run** (`os.execute`: git clone of data, `wget`/`curl` of binaries, `unzip`, `cp`, `cmp`, `mkdir -p`) goes through the sidecar, which uses **busybox sh -c when `busybox.exe` is next to norns.exe**. It was not shipped before: M6 bundles **busybox-w32** (rmyorston, GPL-2.0): sh, cp, cmp, unzip, wget with https, tar, grep, ls, mkdir -p. **MinGit** (git for Windows' portable zip, GPL-2.0, `tools\mingit\cmd\git.exe`) is on the PATH the launcher gives norns (`<app>\tools\mingit\cmd`); `curl.exe` is Windows' own. **Why bundled and not PowerShell shims:** a script's command line is POSIX (`cp -r`, `cmp a b && ...`, pipes); busybox runs it as written, a PowerShell shim per command would not; it needs no administrator rights and no installation, and it is one 1 MB file next to the tools that are bundled anyway. Fetched by the CI job **tools** (`windows/ci/fetch-tools.sh`: MinGit from the git-for-windows releases through the API, busybox from frippery.org; versions and sha256 in `TOOLS.txt` of the zip).
- Paths: the launcher keeps launches relative and ASCII for sclang (as since M1); maiden and go-git use the wide Windows file APIs, the probe installs a script named `Café test script` from a zip. Long paths: the home folder is short by default (`%USERPROFILE%\Verdandi`); a script path over 260 characters would fail in tools that do not use long-path APIs (busybox-w32 and go do, git needs `core.longpaths`, set by MinGit's system config).
- **The Linux shims that apply:** `cmp`/`cp`/`wget`/`unzip`: busybox. `sudo`/`systemctl`: not needed (no systemd; the sidecar answers). The NamAmp `cmp`/`cp` shim (a script's Raspberry Pi `NamAmp.so` is never compared with ours) belongs to the NamAmp Windows build (M7).
- **Plug-in heal** (`windows/launcher/plugin_heal.h`, tested on Linux): before every start the launcher looks at the `.scx` files under `dust\code` and `extensions`; one that is not a **PE file for x86-64** (an ELF from a Raspberry Pi, a Mach-O from a Mac, an ARM or 32 bit Windows file) is moved to `<home>\disabled` with a line in `disabled\MANIFEST.txt` and in the log (SuperCollider would stop at it). `.so` files are never loaded by Windows sclang and are left alone.
- **SC extension seeding:** `<home>\extensions` is an include path of sclang (`sclang_conf.yaml`); packs in the program folder's `extensions-seed\<pack>\` are copied there when the pack is not there yet, never overwritten. **For M7 (mi-UGens and NamAmp for Windows) what is needed:** x86-64 Windows builds of the two plug-in sets (MSVC or MinGW `.scx`, SuperCollider 3.14 plug-in API), their `.sc` classes, put under `extensions-seed\mi-UGens` and `extensions-seed\NamAmp`; for NamAmp the model files and the `cmp`/`cp` shim equivalent for a script that installs its own copy.

## 3. serialosc (item 4)
- **Detect:** serialosc's programs by **exact image name** (`serialoscd.exe`, `serialosc-detector.exe`, `serialosc-device.exe`, `serialosc.exe`) and Windows services whose name is serialosc or whose program is one of them (read-only look at the service manager: no administrator rights needed to look). A held grid port (Verdandi's probe gets "access denied") together with serialosc running is said on the page.
- **SYSTEM > DEVICES > GRID PORTS** has a **SERIALOSC** row while it runs: the help says what it is, that Verdandi needs no serialosc, and how to keep it from coming back. **K3 asks once (`K3 AGAIN`), the second K3 stops it:** the service first (`ControlService STOP`), then the processes of those exact names (`TerminateProcess`, allowed for the user's own processes); the result is on the row and in the log. **A service needs administrator rights to stop**: then the page says so in plain words and shows the exact command to type in an administrator Command Prompt (`sc stop <name>`, and `sc config <name> start= demand` so that it does not start again). Verdandi never elevates and never prompts by itself.
- **AUTO STOP** (off by default): E3 on = `serialosc_autostop=1` in audio.conf; then, when the grid monitor finds a port held and serialosc running, it stops serialosc (at most once a minute) and tries the port again. Only those exact programs and service; nothing else.
- **Tests:** `serialosc_core_test.cpp` (names that must and must not match: `chrome.exe`, `putty.exe`, `serialosc-helper.exe` are not; services before processes; the texts and commands), the page test with a fake status and stop. **Not tested without Windows:** the real process and service enumeration, ControlService, TerminateProcess.

## 5. Found by the CI run (round 1 of M6), fixed
- **A blank in the user's folder name** (the CI's home is `...\user home input`; a real one is `C:\Users\Jane Smith\Verdandi`): a script's shell command such as `cp /home/we/a /home/we/b` had `/home/we` replaced by the real folder **unquoted**, so the path fell in two words and the command worked on other files (the busybox test failed; the git test passed by accident because every word went the same wrong way). `virtual_home.lua` now quotes the replacement for the shell on Windows (escaped outside quotes, as it is inside quotes the script wrote). Test `windows_cmd_quote_test.lua`.
- **maiden's zip install** used `/tmp` for its download (no such folder on Windows: `open /tmp\maiden-...: The system cannot find the path specified`): `windows/maiden/maiden-windows-tempdir.patch` uses the system temp folder (applied to the Windows build only).
- The sclang console wants ESC-ended commands (maiden's web app sends `text` + ESC), not lines: the probe does the same; it works through `ws-wrapper.exe` on the runner (sclang 3.14.1 reads its stdin from the pipe with `-i maiden`).
- Measured on the runner: the norns console (5555) ran a line of Lua through `ws-wrapper.exe`; a page from another site got none; maiden's API and web app answered; git (MinGit 2.56) cloned a repository with a submodule; the plug-in heal moved the ELF and Mach-O files and left the PE one; the seeded pack was copied.
