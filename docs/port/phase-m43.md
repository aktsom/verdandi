# M43: the virtual grid: Ctrl "stage and fire" chord, and a clean switch between the real grid and the virtual grid (Linux desktop only)

Follow-up to M41. Everything new sits behind `VGRID_ROTATE` (= `NORNS_LINUX_DESKTOP` and not `NORNS_WINDOWS`) or in the Linux-only parts of `grid.lua`/`device_list`; macOS and Windows behave as before. This work is independent of M42 (the ext-folder order); M42 was done and committed first, M43 after it.

## 1. Ctrl stage and fire
The owner's cheat codes 2 zilchmos need several keys to go down at nearly the same moment and to come up again; clicking one by one, even with Shift latching (keys go down at the shift release and then stay down), cannot do that.
- **Plain click, drag, right click:** unchanged. **Shift** (hold, collect, release sends, keys stay held): unchanged.
- **Ctrl held:** a click (or a drag) over keys *stages* them: nothing is sent; a staged key has a dashed blue outline (white is Shift's pending set, orange is a latch); a second click on a staged key takes it out. **Ctrl released:** all staged keys go down in ONE write to the device (`vgrid_key_batch`, one `write()` of all the mext key messages), are held for `VGV_CHORD_HOLD_MS` (100 ms, one constant in `vgrid_view.h`), and then all come up in one write. A key that something else holds (a latch) is not pressed again and not let go by the chord: Shift-latched keys stay down while a Ctrl chord fires.
- **Esc** or **losing the window's focus** while staging throws the staged keys away and sends nothing (as for Shift). A chord that has already fired is let go by its own timer; a turn (ROTATE) or a size change clears the staged keys; closing the window forgets everything (the device goes with it).
- **A change from M41:** Ctrl + click used to latch a key (as before M41). Ctrl is now the chord, so the latch is the **right mouse button** only (Shift's keys that stay held, and the right button, are the two ways to hold a key). The Mac keeps Ctrl + click as the latch (the new code is not in the Mac build).
- It only produces ordinary key events: no script-specific code. A hint line in the bottom margin of the window says "Shift = hold    Ctrl = chord".
- The state machine is in `matron/src/platform/linux/vgrid_view.h` (`vgv_ctrl`, `vgv_ctrl_click`, `vgv_ctrl_motion`, `vgv_ctrl_mouse_up`, `vgv_fire`, `vgv_fire_release`); the window wiring in `sdl_bridge.cc` (`grid_do` sends the batches; an `SDL_AddTimer` of `VGV_CHORD_HOLD_MS` posts an event, user code 20, that lets the chord go). The shift/Ctrl state comes from the key events of the shift and Ctrl keys and from `SDL_GetModState` with every mouse event (a key-up that went to another window is found at the next mouse event).
- Limits: two chords fired within one hold time are let go together by the first timer (the second is held shorter); a staged key that is already held by the mouse is not touched.

## 2. Switching between the real grid and the virtual grid
**What was half-way (read from `grid.lua`, `sdl_bridge.cc`, `device_monome.cc`):**
- The virtual grid only joined the list. With a real grid on port 1 it got port 2 (`Grid.new` fills the first free port), so a script on port 1 **stayed on the real grid**; the owner had to choose the device again on SYSTEM > DEVICES > GRID. Toggling the virtual grid off removed it from port 2 and left the real grid where it was. So there was no switch at all.
- Keys held on the virtual grid when it was switched off were never let go for the script (the device was freed with the key still down in the script's own state). Keys held on the real grid while the virtual grid was opened stayed in the script as well.
- The picture the script had drawn was not on the grid that took over (a new device starts dark; the real grid kept its old picture lit while it was not used).
- A script was not told that the grid had changed size when the real grid came back (the removal of the virtual grid fires the port's `remove` callback; no add followed).

**What it does now:**
- Opening the virtual grid makes it the active grid at once: it takes port 1, the grid that had port 1 moves to the virtual grid's place; the picture the script has drawn is copied to the virtual grid in C before the script is told (`dev_monome_copy_leds`, `dev_list_grid_copy_leds`); the grid that was left goes dark unless a script listens on the port it is on now; keys that were down on it are let go for the script (a key-up each).
- Closing it makes the real grid active at once: the picture is copied to it before the virtual grid is removed, keys held on the virtual grid are let go for the script (Lua keeps a table of the keys that are down on each grid, so this does not depend on a key-up that may arrive after the device has gone), the grid that had port 1 before (else any other grid) takes port 1 back, and the script is told again with `Grid.add(real grid)` so that it reads the size again.
- With no real grid: toggling off leaves port 1 empty (no error, no message); the next real grid takes port 1 when it is plugged in. A real grid plugged in while the virtual grid is active waits on port 2 and takes port 1 when the virtual grid goes.
- A size change of the virtual grid is a close and an open: the same switch twice, with the picture carried over both ways.
- All of this is in the Linux desktop only (`NORNS_PLATFORM=linux`): macOS keeps upstream's behaviour (checked by the same Lua test run with `NORNS_PLATFORM=macos`).

## 3. A bug found on the way: the first click after a size change was lost
The headless test lost the first click on the window that is made again by the size buttons, also under a real window manager (openbox). The click never reached the program. Cause: the size changed when the button went down; the window was made again under the pressed button, the release went to a window that was gone, and SDL kept the button as pressed, so the next press was taken as a repeat. **Fix:** the size buttons and ROTATE act when the button is let go over the same button (a click). The test helper no longer needs the click on the dead corner of M41; the test passes without it, on plain Xvfb and under openbox. The M41 note's remark about a first click on a new window was this.
