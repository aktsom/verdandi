# Phase M12: MIDI learn remembers the port; readable long names in the list pages (Windows 0.10.3)

## 1. MIDI learn remembers the port
- **Before:** `S.assign` wrote `dev = "ANY"` for every learned control. A Push 2 in user mode has two ports ("Ableton Push 2 1" the Live port, "Ableton Push 2 2" the User port) that send the same CC and note numbers, so a control left on ANY also moved on the Live messages.
- **Now:** LEARN stores the name norns gives the port the message came from (`d.name` of the MIDI device: one norns device per port, "Name 1" / "Name 2" for the ports of one interface). Every kind that can be learned: encoders E1-E3 (CC), keys K1-K3 (a CC or a note), the arc encoders A1-A4, and the actions (a note, or a CC that becomes a step). The channel stays "any" (only the port was asked for). `lua/core/midimap.lua` (`port_of`, `learn_event`, `take`, `answer`, `finish_action`), `midimap_settings.lua` (`assign` and `assign_action` take the port; no port or an unusable one is ANY, as before).
- **ANY by hand** still works on every row (the DEVICE row of the page lists ANY first). **Existing mappings are not touched:** files load as they are, nothing is rewritten on load (tested: the file is byte-identical after loading).
- **Two ports with the same name:** norns already makes the names unique: the Windows MIDI layer names the ports of one device "Name 1", "Name 2" (`midi_core.h`), and a second device with the same driver name gets a number ("Name 2", "Name 3": `vport.get_unique_device_name`, in the order the devices are listed). The stored name is that unique name, so it is found again after a restart or after the device is plugged in again (a new id each time, the same name). One snag of the old matching rule: a stored name also means every listed name that is it plus a blank and digits ("Foo" is "Foo 2" as well, which is how an interface name stands for all its ports). So when LEARN would store a name that another listed device also matches, it stores `=Foo` (a leading `=`: exactly this name and no other; `V.stored_port`, `V.name_matches`). The DEVICE row shows it as "FOO (THIS PORT ONLY)". Limits that stay: two physically identical devices with no serial number are told apart only by the order Windows lists them in; if that order changes after a restart, the two swap.
- **Tests:** `linux/tests/midimap_layer_test.lua` (through the real layer and midi.lua: learn from port A stores A and ignores the same message from port B; ANY still matches all; replug; restart; keys from a note and from a CC; arc; actions; the answer yes), `midimap_port_test.lua` (the rule, the files, old files unchanged, an exact port survives a file round trip). Two older checks that encoded "learn stores ANY" now say the opposite on purpose.

## 2. Long names in the list pages: no scrolling, an info area at the bottom
- **Common code:** `lua/core/menu/winui.lua`. A row is cut with "..." to fit, label and value share the width (`winui.row_texts`), and nothing scrolls (the marquee of the selected row is gone; `winui.fit` ignores its old scroll and tick arguments). The list is four rows (baselines 8, 17, 26, 35) under which a standing line (baseline 44), a thin rule (y 47) and the **info area** (baselines 55 and 63) are: `winui.list`, `winui.status`, `winui.info`, `winui.wrap2`.
- **What the info area shows:** the full text of the selected row ("LABEL  value") wrapped over two lines, changing at once with E2. A text longer than two lines is cut in the middle: the first line is the beginning, the second starts with "..." and ends with the END of the text (a file type, a port number). When the row's text fits (nothing was cut) the area shows what the page has to say about the row (its help; K3's meaning), or is blank when there is none.
- **Pages moved to it:** SYSTEM > AUDIO (`audio_win.lua`: its boxed 3-line help over the lower part of the screen and its line at the very bottom are the info area and the status line now), GRID PORTS (`gridwin.lua`), MIDI ROUTES (`midiwin.lua`) (their long help sentences still turn to the next two lines every few seconds, only when the row itself is not cut), EXT FOLDERS (`extra.lua`), the file browser of scripts and TAPE (`lua/lib/fileselect.lua`: four rows, the info area shows the full file name, or the folder when the name fits), and the script browser SELECT (`select.lua`: the full name, or the file). **Not moved:** the pages that never scrolled text and whose rows are short fixed words (SYSTEM, DEVICES, MODS, PARAMS, the THEME and SCREEN pages, MIDI MAP): they cut or fit as before. **Could not move to the common code:** the text of the TAPE page's own recording and playing screens (not a list), the PARAMS list (a script's own parameter names, drawn by core code with its own layout), and DEVICES (norns's list with its own scrolling of rows, not of text).
- **Tests:** `linux/tests/winui_info_test.lua` (the cut, the rows, the wrapping: a long device name, a long file name with a long path, non-ASCII names, the same place every time), `audio_page_windows_test.lua` (a long device name: the row cut, the whole name with its end in the info area, changing at once, no movement over time), `fileselect_longname_test.lua`, `extra_folders_page_test.lua`. **CI** renders the AUDIO page with a very long device name in the real program and saves `audio_page_long.png` and `audio_page_short.png` (`windows/ci/maiden_probe.py`, probe `repl-audio-shot`; check `m12-check-audio-shot`; in the output of the run, folder `audio-page`).
