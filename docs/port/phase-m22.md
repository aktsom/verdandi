# Phase M22 (0.10.13): UTF-8 paths, busy console ports, fixed download names, unit tests in CI

Start: `736123b` (nothing newer on `linux-port`). Other open audit findings (second SuperCollider, hung driver call / unbounded wait on the PortAudio worker, sysex, bridge connect thread, duplicate MIDI names) are NOT touched.

## 1. Non-ASCII user and program folders (audit finding 7)
- **Cause:** the launcher uses the wide Windows calls and writes UTF-8 (`sclang_conf.yaml`, environment). `norns.exe`, `sclang.exe`, `scsynth.exe` read environment, command line and file names with the narrow ("ANSI") calls, i.e. in the Windows code page (1252 on a Western PC): `é` arrived as one byte, `Ā` or `Ж` as `A` or `?`.
- **Fix (the reliable one, not an environment conversion):** an application manifest `activeCodePage = UTF-8` (`windows/manifest/verdandi-utf8.manifest`, `.rc`) in every program: norns.exe and ws-wrapper.exe (CMake, RC language), Verdandi.exe and the shims (windres in `build-norns.sh`), sclang.exe and scsynth.exe (`mt.exe` in `build-sc.sh`, merged into their own manifest; the build fails if the text is not in the file). maiden.exe is Go and uses the wide calls. Windows before 10 1903 ignores the manifest (nothing changes there). No effect on audio or latency.
- **Tests:** `linux/tests/utf8_paths_wine_test.sh` (real launcher, stand-ins that use the narrow calls, user AND program folder `José Ā Ж` with blanks: script list, folder checks, data files, rename/remove, tape file, sample read, settings file, logs, sclang's yaml include path) with a control without the manifest that must fail. Wine here starts programs in code page 1252 and honours the manifest (65001), so the difference is real. What Wine cannot show: the real norns/sclang/scsynth and NTFS. The CI on Windows does: `smoke-m1.sh` steps `m22-utf8-manifests` (every exe has the manifest) and `m22-*nonascii*` (a copy of the program folder and a new user folder named with é, Ā, Ж: launcher, Lua boot, script, own data files, script list, sample header, preset, sclang context, audio, tape).
- Not covered: `update-and-run.cmd` in a folder whose name has letters outside the OEM code page (cmd.exe limitation; use the fixed ASCII folder `Verdandi`).

## 2. Ports 5555 / 5556 in use (audit finding 4)
- **Maiden's page can use other ports:** it loads `repl-endpoints.json` from its app folder (host placeholder `maiden_app_location`).
- **Launcher:** before every start (after the stale Verdandi programs were stopped) it checks both ports. A held default port gets the first free port of default+100..199 (never the other console's); the launcher serves maiden's page from a copy (`<home>\.maiden-app`) with the new ports; one plain line (log and the note in the norns window) says which program holds the port (name and process id when Windows tells). No free port: that console is off (program started without the wrapper). `console_port.h`.
- **ws-wrapper:** a port that cannot be opened no longer ends the program (it exited with 1 after 10 s, the launcher took that for the end of norns and stopped everything); it runs on, its output goes to the log.
- **Tests:** `console_port_test.c`; `console_ports_wine_test.sh` (free, 5555, 5556, both; with the old launcher it fails: the stand-in wrapper behaves like the old one); CI step `m22-busy-ports` on real Windows (python listeners on both ports, planned end reached, script ran, log names the program, both consoles answer a websocket handshake on the new ports). Wine cannot name the holder (no TCP owner table): there the line says "another program". The real wrapper part needs the Windows nng DLL; the one at hand does not open ws:// under Wine even on a free port, so it is SKIPPED there and covered by the CI.

## 3. Fixed download names
`Verdandi-windows-latest.zip` (folder `Verdandi`), `Verdandi-windows-asio-latest.zip` (folder `Verdandi-asio`); versioned copies `Verdandi-windows[-asio]-<version>-<hash>.zip` stay as extra release files. Version and build: `VERSION.txt` in the zip, `BUILD.txt`, first lines of `launcher.log`/`norns.log`. The static names are updated only when no check failed (ASIO keeps its own strict gate). `windows/ci/check-static-names.py` checks names and inner folder (build and publish). The versioned names were never needed for a technical reason (they only made a cache-proof link per build); the fix for a stale download is the version in VERSION.txt/BUILD.txt and the sha256 in the release notes.
One-time move: delete the old extracted folder (the data folder in the user's home is separate and untouched), extract the new zip into the excluded folder (Extract All gives `Verdandi-windows-latest`; its inner `Verdandi` folder keeps its name for every later update).

## 4. Unit tests as a CI job (audit finding 8)
`.github/workflows/linux-tests.yml` runs `linux/tests/run_all.sh` in shards (`lua`, `native`, `windows-0`, `windows-1`, `heavy-0`, `heavy-1`) side by side on every push; the Windows build workflow is independent. A test that cannot run says SKIPPED (rc 77 or first line SKIP) in run_all and in the Windows CI report, never PASS. `linux/tests/known-failures.txt` lists tests that fail and why: a listed failure does not break the job, an unlisted one does, a listed one that passes is reported. Stale tests fixed: fileselect_finder, rename, cleanup page.

## The release step and the workflow token (found in the CI of this phase)
Creating the per-commit release (`windows-<hash>`, a new tag) returned HTTP 403 "Resource not accessible by integration" for this branch's commits, although the job has `contents: write`. The probes of the publish step showed why: a draft release and a tag at the commit both answer `X-Accepted-Github-Permissions: contents=write; contents=write,workflows=write`. The history of this branch now changes workflow files (the new `linux-tests.yml`, edits of `windows-m1.yml`), and a token may then make a tag only with the `workflows` permission, which the workflow token cannot have. What the publish step does now (`windows/ci/publish-release.sh`, tested in `linux/tests/release_publish_test.sh` with a stand-in `gh` that refuses tags, and shown to fail without the change): when the per-commit release cannot be made it is skipped, **windows-latest is still updated in place** (its files and its text; the versioned zip copies are among its files), the tag `windows-latest` is not moved, and the notes of the release say so. The links with the static names keep working: `https://github.com/<owner>/<repo>/releases/download/windows-latest/Verdandi-windows-latest.zip` (and `...-asio-latest.zip`). Moving the tag would need a personal access token with the `workflow` scope stored as a repository secret: that is the owner's decision (not done).
