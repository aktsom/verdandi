# Phase M9: support for the script twins on Windows (Windows 0.10.0)

Findings and the three approved changes: `docs/port/twins-update.md`. This note is the approach, written before the code.

## What is built, in order
1. **PortedPlugins pack (the plug-ins twins needs).** AnalogChew, AnalogLoss, AnalogDegrade (GPL-3.0) from the PortedPlugins collection, at the tag v0.4.6 (the version twins' own download is). Built in CI by `windows/ci/build-sc3plugins.sh`, the recipe that builds sc3-plugins and mi-UGens (MSVC, the 3.14.1 headers, `ninja -k 0`, one table in `m7-report.txt` of what compiled and the first error of what did not). The repository's own CMake (`sc_add_server_plugin`) is used, so the whole collection is attempted and the report says how many compile.
   - Ships as a pack in `extensions-seed/PortedPlugins` with `PACK-TARGET.txt = user` (per-user folder `<home>\.local\share\SuperCollider\Extensions`, where twins' installer looks), `PACK-ID.txt`, the class files (each only when its plug-in was built; a class that another pack or SuperCollider already defines is taken out and reported), the licence texts (also those of libraries fetched at configure time), `SOURCE-OFFER.txt`.
   - twins' engine (`lib/engine_twins.sc`) lives in the script's folder and is not part of the pack; the pack contains no other copy (the duplicate-class guard `dup_heal.h` accepts a pack with a `PACK-ID.txt`; the CI report lists cross-pack duplicates).
   - If the three cannot be built: stop and report the options (not to be decided alone).
2. **Markers.** An empty `X_scsynth.so` beside each `X_scsynth.scx` of this pack, so that the script's file-existence test (class file AND plug-in file) passes. Checked in the SuperCollider 3.14.1 source: the server loads a plug-in only when `path.extension() == SC_PLUGIN_EXT` (`.scx` on Windows); the launcher's wrong-architecture heal walks `.scx` files only (`verdandi.c`); CI checks that after a start the markers are still in place, not in `disabled\`, and sclang/scsynth logs have no complaint.
3. **`find -printf`.** busybox-w32 (the bundled one) has no `-printf`. In the Windows shell path, where `/home/we` is already rewritten (`lua/core/virtual_home.lua`, `to_real_shell`), `-printf '<fmt>'` with only `%p` directives becomes `-exec printf '<fmt with %s>' {} \;`. Anything else in `-printf` is left alone. Tested on Linux against GNU find, and on the runner with the bundled busybox and the exact command line of twins' installer.
4. **`nice`, `sudo`, `systemctl` shims.** Three tiny programs in the program folder (like `ws-wrapper.exe`), found through the PATH that the shell path sets: `nice [-n N] cmd ...` runs the rest; `sudo [opts] cmd ...` runs the rest; `systemctl restart|try-restart norns-*` writes `<home>\.norns-request-restart` (norns already acts on it) and exits 0 at once; every other `systemctl` call exits 0 with nothing done. MinGit: `core.autocrlf` of the bundled git is checked (no line-ending rewrite of the owner's files), and `status --porcelain` on a clone made by maiden is checked not to report false changes.
5. **Tests.** CI: a fake git repository ahead of its clone drives twins' real `installer.lua` through `util.os_capture` (library check, update check: `fetch`, `rev-list`, `pull --ff-only`, restart request); a real sclang+scsynth test with a SynthDef that uses the three UGens (a synth is started on the real server); the ten-start restart cycle with the new pack present. Linux: shim logic and the `find` rewrite (GNU find). 
6. **Linux.** The Lua rewrite and the shims are Windows-only code paths (`_norns.listdir`); Linux behaviour and tests are unchanged. If a part helps Linux (an x86-64 PortedPlugins pack) it is said in the report; it is not built here.

## What only the owner can test
twins on a real PC: the screen without "Missing Libraries", sound from the three effects, "Twins Update Available" after the author has pushed, K3 pull and restart through the real window; network access to GitHub from the real machine.
