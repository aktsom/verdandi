# M44 (Linux desktop only): the MIDI auto-connect says every link it sees (a returning virtual MIDI port was silent)

## What the owner saw
Laptop, PipeWire, package 0.10.22-3637. Reaper's virtual MIDI output (`Midi-Bridge:Client-128:(capture_0) Virtual RawMIDI`) was linked to `Verdandi:midi_in` by the M39 auto-connect. Reaper was quit three times and started again each time (once with Verdandi started before Reaper; once the port came back as Client-130). After each quit the log got "midi: ... is gone ...". After each start `pw-link -l` showed the link again and Verdandi followed Reaper's clock, but the log got no "connected" and no "reconnected" line: one "connected" (the first), then three "gone" lines.

## Who makes the link, and where the line was lost
The only code that links a port to `Verdandi:midi_in` is the worker of `matron/src/platform/linux/midi_autoconnect.cc` (grep of every `jack_connect` in the tree: crone's own `Client.h` links audio, `Crone.sc` links the SuperCollider audio, `menu.lua` the MIC links; none links MIDI in). In `apply()` a line was written in one place only: after this worker's own `jack_connect` returned 0 or EEXIST. A wanted port that was **already linked when the worker looked** went through a loop that only remembered it ("linked already ... its going away is said too") and wrote nothing. So the owner's log is what that loop produces when the link at the return was not made by this worker's `jack_connect` in that pass. Two ways that happens, and I cannot tell which one PipeWire does from here (no PipeWire in this container): the sound system restored or made the link itself before the 2 s look, or `jack_connect` returned an error (not 0, not EEXIST) while the link was made all the same (the old code then did `continue` and said nothing, and the next look found the link in place).

## The change (log only; which port is linked and when is unchanged)
- A wanted port that is linked and that this worker had not linked or announced in this run now writes the same line as a link it made itself, with the port name: `midi: connected <port> to Verdandi:midi_in (it was linked already when seen: the link was not made by this program's jack_connect)`, `reconnected` when the port was linked before in this run (after a "gone" line it is said at once, otherwise at most once a minute per port, as before).
- A `jack_connect` that fails writes `midi: could not link <port> to Verdandi:midi_in (jack_connect said <n>); it is tried again`, at most once a minute per port. The next laptop log therefore says which of the two ways it is: plain "connected" (this program made it), "(it was linked already ...)" (the sound system or a person), or "could not link ... said n" followed by "(it was linked already ...)" (jack_connect said no and the link came all the same).
- The port name in every line carries the client number (`Client-130`).

## Tests
`linux/tests/run_all.sh`: "midi:every link that is seen is said, also one the system made (3 quits and returns, port names in the lines)". Scenario `restored` of `linux/tests/midi_autoconnect_test.sh` (probe `probe_midi_restored.lua`): the fake Midi-Bridge client links its own port to `Verdandi:midi_in` itself (`FAKE_MIDI_LINK_TO`, new in `fake_midi.c`), no registration wake-ups (`NORNS_MIDI_POKE=0`), three quits and returns (Client-128 to 131 to 132 to 128). Expected: three "gone" lines, "connected" for 128, 131 and 132, "reconnected" for 128 coming back, no flood. It fails on the old code with four checks: `docs/port/phase-m44-without.txt` (the checks that the links were there and that three "gone" lines exist pass on the old code too: it is the owner's log).
The other MIDI auto-connect tests (conf, env, default, default2, midi_out) are unchanged and must stay green.

## Not changed
macOS (the file is Linux-only), the port choice (`chooseOne`, the default prefix), the 2 s look and the registration wake-ups, the "gone" line and its one-a-minute limit, the Windows build (no auto-connect there).
