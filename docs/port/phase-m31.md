# M31: one Windows zip that covers everything (the ASIO build is the build)

Base: 0b1298ac (M36 pushed). Version 0.10.22 (`windows/VERSION`). Windows build and release files, the AUDIO status note on the window, tests and docs. macOS and the Linux program are not touched (the Linux .deb takes the same version number from `windows/VERSION` at its next build, as designed in M36).

## 1. Reading first (nothing was changed before this was written)

### 1.1 Steinberg's LICENSE file in the ASIO SDK, and Verdandi's licence

**What was read, and what was not.** Steinberg's own repository (`github.com/steinbergmedia/asiosdk`) is not public (404 from here, and git asked for a user name in the first CI run), and `steinberg.net` cannot be reached from the sandbox. The text below is the `LICENSE.txt` of the SDK as it is in the third-party mirror `github.com/audiosdk/asio` that the CI build clones. It is the very file the CI step prints and puts into the ASIO zip as `licenses\ASIO-SDK-LICENSE.txt`, so the owner can compare it with the zip from steinberg.net. It is not Steinberg's own copy.

The lines that matter (verbatim):

> (c) 2025, Steinberg Media Technologies GmbH, All Rights Reserved
> This license applies only to files referencing this license, for other files of the Software Development Kit the respective embedded license text is applicable.
> This Software Development Kit is licensed under the terms of the Steinberg ASIO License, or alternatively under the terms of the General Public License (GPL) Version 3. You may use the Software Development Kit according to either of these licenses as it is most appropriate for your project on a case-by-case basis (commercial or not).
> a) Proprietary Steinberg ASIO License: The Software Development Kit may not be distributed in parts or its entirety without prior written agreement by Steinberg Media Technologies GmbH. ... Before publishing a software under the proprietary license, you need to obtain a copy of the License Agreement signed by Steinberg Media Technologies GmbH.
> b) General Public License (GPL) Version 3: Details of these licenses can be found at: www.gnu.org/licenses/gpl-3.0.html
> Best Practice recommendation: Please refer to the Steinberg ASIO usage guidelines for the use of ASIO, ASIO logo and ASIO compatible logos.

What it allows: use under **either** the proprietary licence (needs Steinberg's signed agreement) **or** the GPL version 3, "on a case-by-case basis". The proprietary option's "may not be distributed ... without prior written agreement" applies to option (a) only; we do not take it and must not sign it (its restrictions would be "further restrictions" that GPLv3 forbids). Under (b) the SDK is GPLv3 code.

**Verdandi's licence.** `LICENSE.txt` is the GPLv3 text; `readme.md` says "GPL-3.0, as norns". The source files of norns carry no per-file notice (no "or any later version" line anywhere in `matron/`, `lua/`, `sc/`, `windows/`; the only "later version" texts are in third-party Faust files under `crone/`). So Verdandi is **GPL-3.0, with no "or later" granted in the files**; I treat it as GPL-3.0-only for this question. Repology lists the SDK 2.3.4 as GPL-3.0-only too (not checked in Steinberg's file, which says just "GPL Version 3").

**Compatible in one zip?** Yes. Both sides are exactly GPL version 3, so the combined work (norns.exe plus a PortAudio DLL built with the SDK) can be conveyed under GPLv3; "only" or "or later" makes no difference when both are version 3. The zip is already a GPLv3 aggregate (SuperCollider is GPL-3.0-or-later, sc3-plugins GPL-2.0-or-later with other free parts, mi-UGens GPL-3.0-or-later, libmonome ISC). What we owe (GPLv3 sections 4 to 6) is what the ASIO zip already carries: the licence text, the notices, and the corresponding source of the binary: `SOURCE-OFFER.txt`, `licenses\`, `source\portaudio-source.zip`, `source\asio-sdk-source.zip`, `source\PA-ASIO-BUILD.txt`. M3 kept ASIO in a second zip out of caution (the licence had been read through mirrors); nothing in the text above requires a separate zip. The one point the owner must accept is that what he distributes is GPLv3 as a whole, which it already was. Not legal advice.

### 1.2 The "ASIO" trademark

- The SDK file only says: refer to "the Steinberg ASIO usage guidelines for the use of ASIO, ASIO logo and ASIO compatible logos" (a "best practice recommendation", not a condition of the GPL option). **I could not read those guidelines** (steinberg.net is not reachable here). So what follows is the careful minimum, not a quotation of their rules.
- What the zip already carries (`windows/pack/ASIO-NOTICE.txt`, in the zip root and in `licenses\`): "ASIO is a trademark and software of Steinberg Media Technologies GmbH", the GPLv3 option, "not an endorsement by Steinberg, the ASIO name is used only to say which driver interface is meant".
- The program uses the word "ASIO" on the AUDIO page and in its log only to name the driver interface (no logo anywhere).
- **Names:** the final file and folder names carry no "ASIO" at all (`Verdandi-windows-latest.zip`, folder `Verdandi`). The only file with "asio" in its name is the temporary copy `Verdandi-windows-asio-latest.zip` that keeps the owner's old update routine working (section 4); naming a file after the interface it supports is descriptive use, and it goes away after the transition. "Verdandi ... ASIO" in a file or folder name is therefore not needed after the transition. If the owner wants the guidelines checked against the notice, they are linked from steinberg.net's developer page; I could not open it.

### 1.3 No driver, a busy driver, a driver that vanishes: today, and what should happen

Everything below was read in the code (`audio_device.c`, `audio_backend_pa.c`, `audio_asio_probe.c`, `lua/core/menu.lua`) and is covered by the stub-driver tests of M19 to M21 (`windows/ci/asio_stub.c` is a real in-process COM driver, registered like an installer does) unless said.

| case | today (the ASIO build) | tested on the runner |
|---|---|---|
| **No ASIO driver installed** | The probe at start lists the registry: `no ASIO driver is registered on this PC`; PortAudio has no ASIO host API (`audio: no ASIO host API: no ASIO driver is installed`); the AUDIO page says `ASIO: no driver installed on this PC` and the entry "low latency: none" cannot be chosen; the program runs on WASAPI (or without sound when the PC has no card) exactly like the WASAPI-only build. If `audio.conf` names an ASIO driver that is not there: the open chain says so (`null audio is used` or `not found, using the default device`) and goes on. | yes: case `none` and the "No Such Driver" input case |
| **Driver busy** (another program holds it) | The start-up probe's `init` is refused: `NOT usable: the driver refused to start: "<its own message>"`; no ASIO host API; the page says `will not start: in use?`; WASAPI as above. If it was chosen and is busy at open: `ASIO driver '...' is busy: another program has it ... Using WASAPI on <the same hardware> instead` (log + AUDIO page + the note on the window). A driver that opens but will not start is closed again and the WASAPI twin is tried. | yes: cases `busy`, `nostart` |
| **Driver vanishes while running** (cable pulled) | The watchdog (M21): no callback for 2 s -> `audio: the card has not called back for 2 seconds: reopening it`; the reopen fails -> mode `fallback` ("no sound", engine on its own clock, no crash), tried again every 3 s, and when the driver answers again the sound goes back; after three stalls within 40 s it gives up with a sentence. **Gap found:** the log and the AUDIO page say it, but the standing note on the norns window (`_menu.audio_note`) was only set once at the start, so a card that vanishes later was not shown on the window. | no ASIO case today (M21 covers null audio and a killed SuperCollider only): **new case `vanish`** |

What should happen, and what M31 adds: never a crash; either sound on the normal Windows path or a plain sentence why there is none, in `norns.log` and on the norns window. The one gap is the window note for a driver that vanishes (or comes back) while the program runs: **the 3-second poll of the window notes now follows the audio state** (`_menu.audio_note_update`, set when the state changes, cleared when the sound is back). The new `vanish` case (stub mode `vanish`, switched by the control file while the program runs) proves: the stall is logged, the program stays up, the window note says `NO SOUND. ...` with the reason, and when the driver is back the sound and the note recover.

## 2. The names (decision, one option recommended)

- **The one zip:** `Verdandi-windows-latest.zip` (inner folder `Verdandi`), `Verdandi-windows-latest.zip.sha256`, `BUILD.txt`, and the versioned copy `Verdandi-windows-<version>-<hash>.zip` on `windows-latest` and on the per-commit release. The link is the existing `https://github.com/<repository>/releases/tag/windows-latest`.
- **What the owner has today:** `C:\Users\<name>\Downloads\Verdandi-windows-asio-latest\Verdandi-asio` with a Defender exclusion on that path. His `update-and-run.cmd` (inside that folder, `FLAVOR.txt` present) downloads `Verdandi-windows-asio-latest.zip`, takes the first `Verdandi*` folder from it and puts it in `...\Verdandi-asio` (the folder it replaces is kept as `Verdandi-asio.previous`).
- **Recommended: the owner does nothing once.** (a) The release keeps publishing `Verdandi-windows-asio-latest.zip` and its `.sha256` as a **byte-identical copy of the one zip** for a transition period. His old updater therefore keeps working, finds the folder `Verdandi` in it, and installs it as `Verdandi-asio`: the same path, the exclusion stays valid. (b) The new `update-and-run` inside the one zip keeps **the name of the folder it runs from** (`Verdandi-asio` stays `Verdandi-asio`, a fresh unpack stays `Verdandi`) and downloads the one name from then on. So after his first update with the old routine, the new routine takes over by itself and no path ever changes.
- **How long the old name stays:** the publish script never removes it (it only adds or replaces). I recommend keeping it until the owner has updated once with the new routine (the first line of `BUILD.txt` of his folder says 0.10.22 or higher, and his next update goes through `Verdandi-windows-latest.zip`; the logs of the updater say which name it fetched), and at the latest 60 days; retiring it is a separate change that the owner asks for. Anyone who unpacks the one zip by hand gets the folder `Verdandi` (no ASIO in the name) and needs an exclusion for that path only if he had none for it.
- **If the owner prefers one clean change:** unpack `Verdandi-windows-latest.zip` once into a folder of his choice and move the exclusion there. Not recommended: it costs work and gains nothing.
- The older versioned ASIO copies (`Verdandi-windows-asio-<version>-<hash>.zip`) already on the release are left alone; no new ones are made.
