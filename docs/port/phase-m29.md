## 1. What twins needs today (read from the current source)
Source read: https://github.com/danielrigler/twins, default branch, commit `870bf17bb633dd3d81660cf25f4d1feed3ea617e` (2026-11-19, "tweaks"): `twins.lua`, `lib/installer/installer.lua`, `lib/engine_twins.sc`, `lib/ugens/`. (`docs/port/twins-update.md` read commit 5dc6206; the installer changed since: it now has a second kind of requirement, "bundled".)

`twins.lua` line 50: `installer:new{requirements = {"AnalogChew","AnalogLoss","AnalogDegrade"}, bundled = {TwinGrain = "lib/ugens"}, zip = ".../schollz/portedplugins/releases/download/v0.4.6/PortedPlugins-RaspberryPi.zip"}`. The engine (`lib/engine_twins.sc`, 828 lines) uses 98 UGen classes. All but five are in the SuperCollider class library (3.14.1 source checked by grep); the other five:

| Library | What twins uses | Where it comes from | Licence | Windows | Linux |
|---|---|---|---|---|---|
| SuperCollider core | ~93 UGens (`In`, `Out`, `GrainBuf`, `PitchShift`, `MoogFF`, `DynKlank` ...) | SuperCollider 3.14.1 | GPL-3.0 | yes | yes |
| sc3-plugins | `Decimator` (DistortionUGens) | github.com/supercollider/sc3-plugins | GPL-2.0-or-later | yes (pack, M7) | yes (apt, and in the .deb) |
| PortedPlugins | `AnalogChew`, `AnalogLoss`, `AnalogDegrade` (required by the installer) | github.com/schollz/portedplugins tag v0.4.6 (twins' zip); Windows builds github.com/madskjeldgaard/portedplugins | GPL-3.0 | yes (pack with markers, M9) | **no** (this phase) |
| TwinGrain | `TwinGrain.ar` (the grain engine; the engine falls back to `GrainBuf` when the class or its plug-in is missing: `useTG`, line 196) | **inside the twins repository itself**: `lib/ugens/TwinGrain.cpp` (source), `TwinGrain.sc.in` (class), and prebuilt `x86_64`/`aarch64`/`armv7l` `TwinGrain.so.in` (the x86_64 one is a stripped ELF, links only libc and libm, needs GLIBC 2.2.5) | **none stated**: the twins repository has no LICENSE file, and neither the README nor the sources say anything (all rights stay with the author) | not required (see below) | required by the installer; the file is already in the script |

How the installer treats each (`installer.lua`):
- A requirement is met when `find` over `/usr/local/share/SuperCollider/Extensions`, `/home/we/.local/share/SuperCollider/Extensions` and `/home/we/dust/code` finds BOTH a class file `X.sc` AND a plug-in `X.so` or `X_scsynth.so`. No version is compared.
- TwinGrain is a *bundled* requirement: it is added to the list only when the installer recognises the machine's CPU from the ELF header of `scsynth` (`od` of `command -v scsynth`, table `{"1:40"="armv7l","2:183"="aarch64","2:62"="x86_64"}`) and the script has `lib/ugens/TwinGrain.sc.in` and `lib/ugens/<cpu>/TwinGrain.so.in`. It is met when `Extensions/twins/TwinGrain.sc` and `TwinGrain.so` are byte-identical (`cmp`) with the script's own files. K3 copies them there (after a load test with python3 `ctypes`; a file that does not load is skipped for good: "using built-in grains"), with no download.
- On Windows `scsynth.exe` is a PE file: the CPU is not recognised, TwinGrain is never added to the list, the engine uses `GrainBuf`. Nothing to do there (and building TwinGrain for Windows is not possible to ship: no licence).
- The three PortedPlugins are met only by files from a pack; K3 downloads the Raspberry Pi zip, which cannot load on a PC.

What was missing, which platform: Linux has no PortedPlugins (the owner's log: `missing AnalogChew/AnalogLoss/AnalogDegrade (class file: NO, server plugin: NO)`), and TwinGrain is "missing" only because nothing copied it yet. Windows is complete.

**Found while reading:** `windows/ci/build-sc3plugins.sh` asks for tag `v0.4.6` of `madskjeldgaard/portedplugins`, but that repository's tags end at v0.4.2; the clone falls back to the head of its default branch (c6c0d74, 2025-02-06). The three classes have the same signatures in both versions (checked), so the Windows pack works and is left alone (it was owner-tested). Linux pins the exact version twins' own zip uses: schollz v0.4.6, commit def734c6d902a0be70caabb6f9f28b810e40f480.

## 2. What changes
1. **PortedPlugins pack for Linux x86_64** (pin `linux/portedplugins.pin`, build `linux/portedplugins-build.sh`): the whole collection is built, each plug-in on its own (`ninja -k 0`; a prototype build here: 22 plug-ins, all of them, 10 seconds, linked only to libstdc++, libm, libgcc_s, libc). Result: `PortedPlugins/` with `Classes/*.sc` and `X_scsynth.so` for each plug-in (Linux names the plug-in `X_scsynth.so`, so the installer's two halves are found without any marker), licence texts, stamp and sha256 list. A class that SuperCollider, sc3-plugins or another shipped pack already defines is taken out and listed (sclang stops at a duplicate class).
2. **Seed** (`linux/portedplugins-seed.sh`, the pattern of `mi-ugens-seed.sh`): before sclang starts, the pack is copied to `<home>/.local/share/SuperCollider/Extensions/PortedPlugins` (temp folder, then rename); newer serial replaces an intact copy of ours; anything that is not ours, a changed copy, or a foreign class with the same name is left alone with one line; `NORNS_PORTED=0` / `ported=0` in audio.conf turns it off; never needs a network. A foreign copy from twins' own Raspberry Pi download (class files, ARM plug-ins) is moved aside into `disabled/` (manifest line, restorable) when our own copy is intact, like the mi-UGens heal.
3. **Both ways of running Linux.** The `.deb`: `linux/package.sh` builds the pack against the bundled SuperCollider source and ships it in `/opt/verdandi/portedplugins`. The checkout: `linux/build.sh` builds it too (a new step, `linux/portedplugins-build.sh`, header files of the installed SuperCollider's version are fetched sparsely, ~seconds, once per pin serial) into `build/linux/portedplugins-pack/PortedPlugins`; `norns.sh` finds it there. No manual step; a failed build is a warning, norns still starts.
4. **TwinGrain** is not shipped (no licence, and the file already travels with the script). What Verdandi does on Linux: before sclang starts, when `dust/code/twins` has the script's own bundled files for this CPU, the same copy the installer's K3 would make is done for the user (`Extensions/twins/TwinGrain.sc` and `.so`, only after the same python3 load test, never overwriting a different TwinGrain that is not the script's, never when the installer's skip marker exists). It is the user's own copy of the author's file moved on the user's machine; `NORNS_TWINS_GRAIN=0` turns it off. See DECISIONS.md.
5. **A check for the next twins change** (`linux/twins-check.sh`): reads the requirement list, the bundled list and the UGen names of twins' engine from the current twins (a shallow clone) or from a pinned list (`linux/tests/twins-pin/`, derived names only, with the commit they came from; `linux/twins-check.sh --refresh-pin` rewrites it), resolves every class with sclang against the shipped packs, and says plainly which library twins needs that nothing ships.
