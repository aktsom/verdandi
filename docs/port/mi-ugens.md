# mi-UGens and nb voice mods (emplaitress) on Linux x86_64: findings and plan

Investigation only; nothing in the product was changed. Everything below was read from source or measured in a scratch directory with the bundled SuperCollider 3.14.1 (the one `linux/package.sh` builds, copied out of a built `.deb`), a headless norns (`linux/tests/norns_probe.sh`) and a JACK peak meter written for the purpose. Where I could not check something it says so (section 6).

## 0. Verdict in four lines

- **Plug and play is achievable cleanly**, for this mod and for any mod that needs mi-UGens: ship an x86_64 build of mi-UGens with the package (built from a pinned source in `linux/package.sh`, as sc3-plugins already is) and put it where the mod looks, **before SuperCollider starts**. The mod then never downloads anything and the first restart after enabling it works.
- **The place matters**: the package's usual place (SuperCollider's system extension folder) is not enough for this mod: it only looks in the user's extension folder, so it fetches the Raspberry Pi files anyway, and with both present SuperCollider refuses to compile (duplicate classes). Measured, section 3.
- **Not everything is fixable from our side**: scripts that bring their own installer for a different Raspberry Pi pack (two found: pedalboard, krill) will still fetch ARM files and can collide with ours. A startup check (section 5) makes that visible instead of a silent "SUPERCOLLIDER FAIL".
- Smallest first step: section 6.

## 1. What emplaitress does (read from a fresh clone, commit `5ababb1`, 2024-02-18)

`lib/mod.lua` and `lib/emplaitress.sc` (the folder has only these two files and a README: "install it, turn on the mod, restart twice, the first time supercollider might fail").

| question | answer (file, line) |
|---|---|
| where does it get the pack from | `lib/mod.lua:383`: `wget --quiet https://github.com/schollz/oomph/releases/download/prereqs/mi-UGens.762548fd3d1fcf30e61a3176c1b764ec1cc82020.tar.gz -P /tmp/` (a release asset of another script, oomph) |
| which platform | **always the same file, no machine check**. I downloaded it: sha256 `9412622a99d703a4c5803c1568ca174d2607d60390c9313ad2762445051708ce`, 2.6 MB, every `.so` is `ELF 32-bit LSB shared object, ARM, EABI5` (the Raspberry Pi norns). The name carries the mi-UGens commit it was built from, `762548f` (2021-08-07, per-project folder layout; today's repository has a top-level CMake). |
| where does it put it | `mod.lua:384`: `tar -xvzf /tmp/<file> -C /home/we/.local/share/SuperCollider/Extensions/` then `rm`: the **user** extension folder only (`/home/we` is the virtual home: `~/Verdandi/.local/share/SuperCollider/Extensions/mi-UGens` on the owner's laptop, as seen there) |
| does it skip the download | `mod.lua:380`: `test -n "$(find /home/we/.local/share/SuperCollider/Extensions/ -name MiPlaits.sc)"` in the `system_post_startup` hook. **Only that one folder is searched** (not the system extension folder, not `dust`). If the file is found it prints "emplaitress found mi ugens", otherwise it downloads and prints "PLEASE RESTART". |
| why two restarts | a class file in `dust/code/<name>/lib/*.sc` is compiled by sclang at its start **whether or not the mod is enabled**. Restart 1 (after installing and enabling): sclang compiles `Emplaitress`, `MiPlaits` is not there yet, SuperCollider fails; the mod's hook (which runs in matron, independent of SuperCollider) then downloads the pack. Restart 2: the pack is there, it works. |
| what it creates at startup | one class, `Emplaitress` (`emplaitress.sc`): its `initClass` calls `StartUp.add { ... }`; inside that function: the SynthDefs `\plaitsPerc` and `\plaitsADSR` (both use `MiPlaits.ar`, `LeakDC`, `OnePole`, `DetectSilence`, `Pan2`, `EnvGen`), then OSCFuncs on the address families `/emplaitress/perc`, `emplaitress/note_on`, `emplaitress/note_off`, `emplaitress/note_mod`, `emplaitress/note_simple_mod`, `emplaitress/stop_all`, and (after 10 s, `Server.default.sync`) six groups and the line "ALL HAIL THE EMPLAITRESS". The Lua side adds four nb players "emplait 1".."emplait 4" in the `script_pre_init` hook and needs the **nb mod** (`note_players` is the nb library's global: without it the mod's `script_post_cleanup` hook errors, seen in my runs; unrelated to the pack). |

**Why one missing class stops SuperCollider, enabled or not** (measured, run A below): the `StartUp.add` function is run by `Meta_StartUp:run`, which loops over all registered start-up functions; `MiPlaits.ar` on a missing class raises "Message 'ar' not understood" inside that loop and the loop is abandoned. The trace in `sclang.log` shows it: `FunctionDef in Method Meta_Emplaitress:initClass` <- `Function:doOnStartUp` <- `ArrayedCollection:do ... var i = 2` (of 6) <- `Meta_StartUp:run`. The start-up functions after index 2 never run (the engine list never appears, so norns' own start-up is among them): no "engines:" line, matron times out: "SUPERCOLLIDER FAIL". This is exactly the owner's log.

**Other scripts with the same pattern** (read in the catalog clones, not run): `pedalboard` (`lib/ui/util/mi_ugens_installer.lua`: `wget .../okyeron/mi-UGens/raw/master/linux-norns-binaries/mi-UGens-linux-v.03.tar`, copies a flat layout into the same user extension folder) and `krill` (README: PortedPlugins, mi-UGens as 32-bit ARM). Their archives differ from the oomph one, so a fix that answers one URL does not cover them.

## 2. The pack

**Source and releases.** `github.com/v7b1/mi-UGens` (the upstream of the pack; the ARM builds the scripts fetch are builds of it, oomph's from commit `762548f`; `okyeron`'s repository carries ARM binaries too). Tags `v0.0.1` .. `v0.0.9`; `v0.0.9` is `10f6824` (2026-04-10). Its CI (`.github/workflows/build.yml`) builds on macOS, Ubuntu and Windows and uploads `mi-UGens-Linux.zip` to each release: **an official x86_64 Linux asset exists**. I downloaded it (`.../releases/download/v0.0.9/mi-UGens-Linux.zip`, 2,658,472 bytes, sha256 `50ebdf30...309e`): 12 plug-ins `Mi{Braids,Clouds,Elements,Grids,Mu,Omi,Plaits,Rings,Ripples,Tides,Verb,Warps}.so` (the twelve of the repository), x86-64, plus `Classes/` and `HelpSource/`. (The GitHub API refused me from this sandbox, so I could not list the releases page itself.)
- `Classes/MiPlaits.sc` of the ARM pack (`762548f`) and of `v0.0.9` are byte-identical (`diff`), so emplaitress's `MiPlaits.ar(...)` keyword arguments work with the new pack.

**Licences** (read in the tree at `10f6824`):

| part | licence | what it asks |
|---|---|---|
| the UGen wrappers (`projects/*`, `sc/Classes`), Volker Böhm, 2020 | **GPL-3.0-or-later** (headers; `gpl-3.0.md` in the root) | same licence as this project: compatible; they include SuperCollider's GPL headers |
| the Mutable Instruments code (`eurorack/plaits`, `rings`, `clouds`, `braids`, `elements`, `tides2`, `warps`, `stmlib`), Emilie Gillet, 2012-2021 | **MIT** (every file has the header; `eurorack/LICENSE.txt`) | keep the copyright and permission notice in copies; no non-commercial clause found (grep for "non-commercial", "Creative Commons", "CC-BY" in these folders: nothing). `stmlib/programming/serial` is GPL (not built into the plug-ins) and `avrlib` third-party FatFs is not built either. The hardware designs are CC-BY-SA, not part of the code. |
| `libsamplerate` (a submodule of MiBraids, statically linked into `MiBraids.so`) | **BSD-2-Clause** (Erik de Castro Lopo, `COPYING` in the submodule) | reproduce the notice with a binary distribution |
| the Linux release zip itself | **contains no licence file at all** | if we ship binaries we must add the notices ourselves (GPL-3 text, the MIT notice, the BSD notice, the source address), like `/opt/verdandi/licenses/sc3-plugins/` today |

The project's rule (GPL-3.0, list every dependency in `DEPS.md`) is met; I did not check the speech data files of Plaits (the word lists of its speech engine) for a separate claim: the repository states MIT for them, I cannot verify that independently.

**Building it here.** `cmake .. -DSC_PATH=<SuperCollider source tree> -DCMAKE_BUILD_TYPE=Release && make install` as in the README; `SC_PATH` has to be a SuperCollider **source** tree (it uses `include/plugin_interface` and `include/common`): `linux/package.sh` already clones `Version-3.14.1` into its cache (`$CACHE/supercollider`). I built `v0.0.9` against that tree: **13 seconds** on this machine, no dependency beyond a compiler, cmake and the `libsamplerate` submodule (`git submodule update --init`, pinned `2ccde95`). Two things to know: (1) a first `make -j` failed with "No rule to make target .../libsamplerate.a" (a target race); building the `samplerate` target first, or a second `make`, fixes it; (2) the build writes into the source tree (a `build` folder inside the submodule): use a copy. Result: 12 `.so`, 3.48 MB, linked only to `libstdc++`, `libm`, `libgcc_s`, `libc`, highest symbol versions GLIBC_2.27 and GLIBCXX_3.4 (loads on Ubuntu 18.04 and later). **My build is byte-identical to the official Linux release asset** (`cmp` of all 12 `.so` and `diff` of `Classes/`: identical), so the build is reproducible with this toolchain and can be verified against upstream's file. Installed size 3.5 MB (53 KB of it help files); upstream's zip is 2.6 MB.

**Where SuperCollider looks** (from `sclang.log`, "Compiling directory" lines, and the runs below): `/opt/verdandi/supercollider/share/SuperCollider/SCClassLibrary`, then `.../share/SuperCollider/Extensions` (the **system** extension folder: where `linux/package.sh` already installs `Extensions/SC3plugins`), then `$HOME/.local/share/SuperCollider/Extensions` (the **user** folder), then the launcher's `sclang_conf.yaml` include paths (`sc/core`, `sc/engines`, the whole `dust`). Plug-ins (`.so`) are found in the same extension folders. Both folders work, measured.

## 4. Design options against "plug and play"

**(A) Ship the x86_64 pack with the package.** Two variants, only one of which works with this mod:

- **A1, system extension folder** (`/opt/verdandi/supercollider/share/SuperCollider/Extensions/mi-UGens`, next to SC3plugins; the natural place): works for scripts that merely use the classes (run J), but **fails with emplaitress** (run G): its check does not look there, it downloads ARM files beside ours: ELF error on the first boot, duplicate classes after. Not acceptable alone.
- **A2, the user extension folder, put there by the launcher before sclang starts** (the package stores the pack outside every scanned folder, e.g. `/opt/verdandi/share/mi-UGens/`, so nothing is compiled twice; `linux/norns.sh` copies it to `~/.local/share/SuperCollider/Extensions/mi-UGens` if that folder is not there and nothing else defines the `Mi*` classes, and writes a stamp file `.verdandi-pack` with the package version). Works as run C: the mod's `find` succeeds, no download, **and the first restart after enabling already works** (SuperCollider compiles the mod's class with `MiPlaits` present; there is no "restart twice"; the failure of run A cannot happen). A copy, not a link: `find` does not follow a linked folder, and a link would dangle after the package is removed.
  - *fresh install on another computer:* first launch seeds the folder (3.5 MB, below a second); installing the mod from maiden works at the first restart after enabling. Nothing else for the user to do.
  - *machine that already has the ARM pack* (the owner's first state): the folder `mi-UGens` exists, so the launcher does not touch it; the plug-in check prints its message as today. Suggested improvement (decision for the owner, not built): add to that message "this version ships an x86_64 mi-UGens: move that folder away and it is installed at the next start". Never deleting or moving files by itself stays the rule of that check.
  - *package size and notices:* about +2.6 MB compressed (the deb is 13.8 MB today), +3.5 MB installed; `licenses/mi-ugens/` with the GPL-3.0 reference, the MIT notice (Emilie Gillet), the BSD notice (libsamplerate) and the source commit; a line in `DEPS.md` and in `SOURCES.txt` of the package.
  - *updates:* a new package carries a new stamp; the launcher replaces the seeded folder only when the stamp file says it is ours (a user-installed or foreign folder is never touched). Removing the package leaves the 3.5 MB copy in the home (harmless; stated in the manual).
  - *duplicate classes with other scripts:* the launcher seeds only when no other file named `Mi*.sc` exists in the user or system extension folders or in `dust`. A script that installs its own flat copy later (pedalboard, krill: the okyeron ARM archives) collides with ours: `duplicate Class found` and ARM plug-ins; that is the case section 5's check reports, with both file names.

**(B) Intercept the mod's download** (a `wget` shim in `linux/shims`, which the launcher already puts first on the PATH of norns and everything its scripts run, next to the `sudo` and `systemctl` shims): the shim answers the download of that one URL with a tarball of the x86_64 pack, the mod's own `tar` unpacks it into the user folder. Measured (run I): works, but **only from the second start** (the first start still fails: the pack arrives after sclang compiled), the shim must know each script's URL and archive layout (the oomph archive here; pedalboard's and krill's differ), and it depends on `wget` being installed. It is a fallback, not the main path.

**(C) Leave it to the user**: the user moves the ARM folder away, installs an x86_64 pack by hand into the right folder, restarts; every new mod or fresh install repeats the problem. Not plug and play; it is what the owner did.

**Combination I would build:** A2, plus section 5's check; B only if more scripts turn up that ask for exactly this archive.

## 5. The missing-class check (proposed, not built)

In the style of the wrong-architecture check (`plugin_arch_check`, reports before start, never moves anything) and the duplicate-engine message in `lua/core/startup.lua`:

- **When:** after sclang has started and either `engines: [` appeared or the start-up timed out (`norns.startup_status.timeout`, where `startup.lua` already decides between "DUPLICATE ENGINES" and "SUPERCOLLIDER FAIL"), and at most once per start.
- **What it reads:** the last 2000 lines of `sclang.log` (read only, bounded). Patterns: (1) `Execution warning: Class 'X' not found` followed by `ERROR: Message ... not understood` and a trace containing `Method Meta_Y:initClass` (or `Meta_Y:...`): class `Y` needs `X`; (2) `ERROR: duplicate Class found: 'X'` followed by the file line sclang prints; (3) `Superclass 'Z' of class 'Y' is not defined`.
- **Finding the folder:** map `Y` to the file that defines it with `grep -l "^Y *{" ` over `dust/code/**/*.sc` and the extension folders (fixed-string match, quoted arguments, no shell expansion of log text), then name the top folder (`dust/code/emplaitress`).
- **Output:** one line to the log and to the terminal: `norns.sh: SuperCollider stopped: class Emplaitress (dust/code/emplaitress/lib/emplaitress.sc) needs the UGen class MiPlaits, which is not defined. Likely cause: the plug-in pack mi-UGens is not installed in an extension folder, or its files are for another machine (see the PLUGINS line above). Nothing was changed.` plus, for a known family, a hint (`Mi*` -> mi-UGens; the pack Verdandi ships, section 4, is installed automatically if ...); for a duplicate: both file names and "one of them has to go". And a standing note on the window through the existing `_norns.set_warning` (the same mechanism as "PLUGINS: wrong-architecture plug-in, see log"): `SUPERCOLLIDER: class MiPlaits missing (emplaitress), see log`, cleared when the next start has no finding.
- **Safety:** read-only; bounded input; no evaluation of anything from the log; paths only taken from the file system, never from the log text; limited to `dust/code` and the extension folders; no network; if the log cannot be read or nothing matches it says nothing (the existing "SUPERCOLLIDER FAIL" stays); the three patterns are anchored on sclang's fixed message formats and tested with the real log of run A and run G as fixtures.
- **Needs:** about 150 lines (shell or Lua in `startup.lua`; a small C++ helper only if the grep is too slow), the two fixture logs, tests in `run_all.sh` (the headless boot with a fake class that uses a missing UGen, as in run A, must print the line and set the note), a manual paragraph, a hardware-checklist item.

## 6. Recommendation

1. **Do A2**, because it is the only variant that makes the owner's sequence (install from maiden, enable, restart) work at the first restart, with nothing downloaded, and it is the cleanest in the licence/size/update sense: a pinned source build in `linux/package.sh` (the sc3-plugins section is the pattern), upstream's own Linux release asset as a check of the build (same bytes), a launcher step that seeds the user folder, a stamp, the notices.
2. **Smallest first step:** build mi-UGens in `package.sh` into `/opt/verdandi/share/mi-UGens` (pinned `v0.0.9`, `10f6824`; submodule `2ccde95`; compare with upstream's Linux zip) + the licence notices + the launcher seeding step + a headless test (the fake-mod boot of run C: mod folder present, enabled, **no** download, the "ALL HAIL" line appears and the meter hears a note). Then the check of section 5 as step two.
3. **Effort (a guess, labelled as one):** the package build and notices about half a day; the launcher step with stamp and the "nothing else defines Mi* classes" test about half a day; the tests (headless boot with the real pack, meter, an update case, a foreign-pack case) one day; the check of section 5 about a day; about three days in all, plus one clean-root package build (about ten minutes) to prove it end to end.
4. **Decision gates for the owner:** shipping third-party binaries (GPL-3.0-or-later wrapper, MIT, BSD-2: compatible, notices needed); the launcher writing into the user's extension folder (visible in the manual); whether the ARM-pack message should offer or perform the move (the current rule: never moves).

**What I could not verify:** the owner's laptop (Mint, PipeWire, the real maiden install flow, the nb mod from the catalog, a real grid or keyboard playing the four voices); anything about sound quality (I measured that a note produces signal, peak 0.45, not how it sounds); the GitHub releases list (API refused); other scripts' installers beyond reading their source (pedalboard, krill: not run); the pack under another glibc than this machine's (the symbol versions say 2.27 at most); whether Plaits' speech data carries a claim other than the repository's MIT statement; Windows (not applicable: Windows packaging is a later phase and has its own plug-in folders).

## Appendix: how to reproduce

Scratch directory, nothing in the repository: `git clone https://github.com/sixolet/emplaitress`, `git clone https://github.com/v7b1/mi-UGens` + `git submodule update --init`, `cmake -DSC_PATH=<the package cache's supercollider source>` and `make samplerate && make install`; the bundled SuperCollider copied from a built `.deb` (`/opt/verdandi/supercollider`, it needs to be at that path: the prefix is compiled in, I linked it there for the runs and removed the link afterwards); a home with `dust/code/emplaitress`, optionally `dust/data/system.mods` listing it and `.local/share/SuperCollider/Extensions/mi-UGens`; `PATH=<bundled sc>/bin:$PATH NORNS_HOME=<that home> linux/tests/norns_probe.sh <probe.lua>`. The probe waits 14 s, starts the JACK peak meter (a 30-line C client) and sends the two OSC notes.
