# M35 part A: the checkout build is as complete as the package

Base: 985caf9 (M34 pushed and green). Version line 0.10.22 (Linux only; `windows/VERSION` is not touched and no Windows zip is made or republished). Shell scripts and tests only; no C, Lua or Windows file changes. Part B (the one-click install) is a plan only: `docs/port/phase-m35-deb.md`.

## What was wrong

A checkout built with `linux/build.sh` had no x86_64 mi-UGens pack. Only `linux/package.sh` built it (`build_mi`), for the .deb. So on the owner's test copy the mods `emplaitress` (MiPlaits) and `fx_resonator` (MiRings) stopped SuperCollider with "Message 'ar' not understood" (the class is nil), and since sclang stops at the first error the whole SuperCollider failed to start even with those mods off. A Raspberry Pi copy of the UGens that `emplaitress` downloaded was correctly moved to `disabled/` (wrong architecture) and nothing took its place. The owner's installed Verdandi (the .deb) has the pack, so there the mods work.

## A1: one recipe for the package and for the checkout

- New `linux/mi-ugens-build.sh`. `build <work> <SuperCollider dir>` is the recipe that was `build_mi()` in `package.sh`, moved unchanged in what it does (clone the pinned tag, fetch pull request 24, merge, cmake with `-DSC_PATH`, build `samplerate` first, install, strip, remove help, copy the three licence texts, stamp with `mi-ugens-seed.sh stamp`). `checkout [repo]` is what `linux/build.sh` runs.
- `package.sh build_mi` now only calls `mi-ugens-build.sh build "$CACHE" "$CACHE/supercollider"`, so it writes to the same places as before (`$CACHE/mi-ugens-pack/mi-UGens`, the licence files next to it); `build_tree` and the .deb are unchanged. There is no second recipe.
- **Source tree against installed headers.** The package builds against the SuperCollider 3.14.1 SOURCE tree it builds for `/opt/verdandi`. A checkout has only the installed SuperCollider (Ubuntu 24.04: 3.13.0) and no source. The mi-UGens CMake only uses `include/` and `common/` of that tree (`-DSC_PATH`), and `portedplugins-build.sh headers` already fetches exactly those two folders (a sparse shallow clone, seconds) at the tag of the installed `scsynth -v`. So the checkout step reuses that: `mi-ugens-build.sh checkout` calls `portedplugins-build.sh headers` (new small subcommand `sc-tag` gives the tag) and builds against them. The plug-in interface (version 3) is the same for 3.13 and 3.14, so the pack works with the installed SuperCollider. I built it here against the 3.13.0 headers and the real 3.13.0 sclang/scsynth loaded and rendered MiPlaits and MiRings.
- The pack is built into `<repo>/build/linux/mi-ugens/mi-ugens-pack/mi-UGens` with a `.built-for` marker (serial, commit, pull request commit, SuperCollider tag): built once, and again only when `linux/mi-ugens.pin` or the SuperCollider version changes. The network is needed once (git clone of the pinned tag and of pull request 24, SuperCollider headers). A failure is a WARNING and exit 0, `NORNS_NO_MI=1` skips it.
- `linux/norns.sh`: `NORNS_MI_PACK` defaults to `$REPO/mi-ugens/mi-UGens` when that exists (the .deb), else the checkout's pack (like `NORNS_PORTED_PACK`). The seeding code is not changed: `mi-ugens-seed.sh seed` (stamp, checksums, update by serial, never overwrites what is not Verdandi's, the Raspberry Pi copy is moved aside by the heal step before sclang starts, no duplicate classes). `plugin-heal.sh` knows the same default so it does not treat the pack as missing.
- Measured here (4 cores): mi-UGens pack 19 s, 13 plug-ins, 3.7 MB (stripped, no help), plus the headers (a few MB, in `build/linux/mi-ugens/sc-headers`) and the clone (`build/linux/mi-ugens/mi-ugens`, with its build tree, some tens of MB; `build/` is not in git).

## A2: a missing tool is named with the install command

- New `linux/tools-hint.sh` (sourced): `missing_tools_warning "<what is not built>" tool...` prints "WARNING: X was not built, because these tools are not installed: cmake ninja" and "install them with:  sudo apt install cmake ninja-build", then "or run linux/setup-deps.sh ... Verdandi starts without this part". It maps each tool to its apt package (ninja is `ninja-build`, c++/strip are `build-essential`, go is `golang-go`, xz is `xz-utils`).
- Used by `mi-ugens-build.sh`, `portedplugins-build.sh` (which only said that a tool was not installed, with no command), `maiden-build.sh` (git curl tar xz sha256sum go) and at the top of `linux/build.sh` for the main build (git, python3, pkg-config, compiler: nothing can be built without them, so it stops, but with the command). The optional parts (maiden, PortedPlugins, mi-UGens) never stop the build: they warn and `build.sh` goes on.
- `linux/setup-deps.sh` stays the one place that installs everything; it lacked `xz-utils` (maiden unpacks node with `xz`), `tar` and `coreutils` (always present in practice): now listed. A test checks that every package a message can name is in its apt list.
