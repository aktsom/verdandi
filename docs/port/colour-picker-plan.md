# Colour picker for the hex colour rows, and two renames (BUILT; the plan is revised: the norns screen only, no panel)

Linux desktop build only. `macos/` is only read; everything is behind `NORNS_PLATFORM` (Lua) and `NORNS_LINUX_DESKTOP` (C). One picture: `colour-picker-previews/picker-live.png`, a capture of the real window.

**Revision.** The first plan proposed a strip panel drawn in the main window (hit-testing, mouse wheel and click on strips, a panel frame-time test, two stand-in pictures). The owner rejected it: the picker uses **only the norns screen's param menu**. All of the panel (`picker_skin.c`, panel drawing, strip hit-testing, wheel and click mapping on strips, its pictures and generator) is removed from the plan and was not built. A colour wheel was considered and rejected earlier: it is one control with two values, the menu's idea is one value per row.

## 0. Renames (visible names only)
The SYSTEM page **UI** is called **SCREEN** and **BOX** is called **THEME**: in the SYSTEM list (`"SCREEN >"`, `"THEME >"`), the pages' own text and comments, the manual, `RUN-ON-LAPTOP.md`, `HARDWARE-CHECKLIST.md` and the tests that look for the names. **The page ids stay `UI` and `BOX`** (`_menu.set_page("BOX")`, `m["UI"]`), the ids `SCREEN` and `THEME` are accepted as aliases of the same modules, and the files stay `ui.conf`, `box.conf`, `box-presets/*.box`. The older plans keep the old names (they are history).
*What a file rename would involve (not done; recommended against):* new names `screen.conf`, `theme.conf`, `theme-presets/*.theme`; `ui_settings.lua` and `box_settings.lua` read the new name first and fall back to the old; the first start after the update copies (never moves) the old file to the new name when the new one is absent, and the presets file by file, the old ones staying for a downgrade; writes go to the new names only; CLEAN UP, the tidy script, `norns.sh`, the package scripts, the manual's file table and about ten tests name these files and would change; two copies exist until the owner deletes the old ones.

## 1. How the hex rows and the text entry worked, and where the picker fits
THEME's five colour rows and SCREEN's HEX row opened the text entry on K3 (`lua/lib/textentry.lua`, with the desktop changes: 6 digit limit, hint line, key interception, and since the last fix the arrows and value keys as E2/E3). The new value went through `box.set_part` / `ui.set_custom`, which store, **apply** (`_norns.box_look`, `_norns.ui_look`: an event to the window, which makes the layers again) and **save** at once. Menu pages get their keys from `_menu.keycode` (`lua/core/menu.lua`): with the launcher's `NORNS_HARDWARE_KEYS=1` the keys `1 2 3` are K1-K3, Enter/Space K3, Esc/Backspace K2, `Q W / A S / Z X` E1-E3 (Shift x5); in the menu UP/DOWN are E2, LEFT/RIGHT are K2/K3, `-`/`=` are E3 (a release arrives as delta 0 and must change nothing); F1-F4 are global; a page that defines `keycode` gets every other key.

## 2. The design (as built)
**A menu page `PICKER`** (`lua/core/menu/picker.lua`, registered with the computer pages in `menu.lua`), opened by K3 on a colour row (`box.lua`: `m.open_picker(row)`, `ui.lua`: `m.open_picker()`), with the rows **HUE, SATURATION, BRIGHTNESS, HEX**, each changed like any param:

| input | does |
|---|---|
| E2, UP / DOWN | choose the row |
| E3, LEFT / RIGHT, `-` / `=` | change the row by a step (5 degrees of hue, 5 percent). **Shift** = 5 steps (25), **Ctrl** = a fine step of 1. Hold: a repeat is two steps like on other pages; **a release changes nothing**; the values clamp at both ends (hue 0-360, no wrap) |
| PageUp / PageDown, Home / End | 5 steps; smallest / largest value of the row |
| K3 (Enter) | keep and save (**once**); on the HEX row: open the text entry |
| K2 (Esc), F1-F4 | give the old colour back; nothing is written (F keys and any other page change run the page's `deinit`, which restores) |
| `H` | open the text entry (3 or 6 digits, with or without #); the rows follow what is typed |
| `C` | centre: **hue 180, saturation 50, brightness 50 = `#408080`**, with the live preview |
| `R` | back to the colour the picker opened with |
| Ctrl+C / Ctrl+V | copy the code / paste one (section 3) |
Every handler ends with a redraw (the lesson of the THEME bug), is wrapped in `pcall` (an error is logged as one `PICKER page:` line and leaves the page whole), and the keys the picker does not use return `false` so the menu's own bindings apply (a one-line change in `_menu.keycode`: a handler that answers `false` falls through; every existing handler returns nothing, so the device is unchanged).
**Live preview:** every change is applied to the thing being edited without storing or writing: `box.preview_part(part, hex)` and `ui.preview_custom(hex)` call `_norns.box_look` / `_norns.ui_look` only; OK calls the page's normal `set_part` / `set_custom` (store, apply, save once); cancel calls `box.apply()` / `ui.apply()` (what is stored). The window draws the box the quick way while the colour keeps changing and the crisp picture follows about 180 ms after the last change (the resize path of `box-style-plan.md` section 8).
**Opening state:** on a valid colour the rows are exactly where that colour is (the picker keeps the exact floats: hex -> HSB -> hex is the identity for every 24 bit colour), nothing is applied and OK without a move changes nothing. With no valid colour (the SCREEN HEX row before one was entered; a damaged value) the rows start at the middle and the page says "not set". **Greys, black and white** have no hue: the picker keeps the last hue it held (a session value, first 180), so raising the saturation again does not jump; moving one row never changes the other two (bit for bit).
**The norns screen** shows the heading (`THEME KEYS`), the three rows each with a small bar and a marker and the value, `HEX #RRGGBB` and a hint line. The screen is grey (the SCREEN look tints it), so **a colour swatch next to HEX cannot show the colour**: the colour is on the box, the keys, the encoders, the buttons, the font or the screen itself while the picker is open. A luminance-only swatch would mislead, so none was built. **No strips are drawn, so the floor of 25 on degenerate strips is dropped.** Recent colours: dropped.
**How it returns:** the page that opened the picker gets its row, scroll and message back (`take_returning` in its `init`). The text entry opened from the picker restores the picker's handlers (`reclaim`).

## 3. Copy and paste
**Ctrl+C** on a colour row of THEME or SCREEN's HEX row, in the picker and in the picker's text entry copies the current code (`#3B6EA8`) to the system clipboard with a short message (`copied #3B6EA8`). **Ctrl+V** pastes: 3 or 6 hex digits with or without `#` (blanks and a trailing newline are fine); in the picker the colour is applied live (K3 keeps it), in the text entry it replaces the text, on a colour row of the page it is applied **and saved** (the page's own action). Anything else shows a short message and changes nothing: `clipboard is empty`, `clipboard text too long`, `clipboard is not text`, `not a colour: hello`, `no clipboard` (a build without the binding).
**How:** `_norns.clipboard_set(text)` and `_norns.clipboard_request()` (`weaver.cc`, Linux only) post events to the window's thread (SDL's clipboard belongs to it); the window reads the clipboard and answers through the event queue with `_norns.clipboard_text(text, status)`; the answer is applied only if the page that asked is still the current one (a late answer after the picker opened, or the entry closed, is ignored: found by the stress test). The window **looks at no more than 65 bytes** (`matron/src/platform/linux/clip_text.c`): an empty clipboard, more than 64 characters (`long`: the text is not given) or a control character (`binary`) are reported as such; a 50 MB text is never walked through (SDL itself returns the whole string, which is freed at once; a limit on SDL's own read is not possible).
**No clash:** Ctrl+O, Ctrl+Q, Ctrl+M and Ctrl+Shift+S are taken by the window before the keys reach Lua (`desktop_shell_linux.cc`) and the pages do not use them (tested); `Ctrl+C` and `Ctrl+V` are used only on a colour row, in the picker and in its entry (the pages answer `false` elsewhere: scripts, other rows and other pages get the keys as before; scripts only read the keyboard outside the menu); in the text entry Ctrl+C and Ctrl+V never type a `c` or a `v`. Ctrl+S alone is still the hardware key E2 (as before). **X11 and Wayland:** SDL uses the display system's own clipboard; on Wayland it works while the window has the keyboard focus (it does, a key was just pressed); what is on the clipboard after Verdandi exits depends on a clipboard manager (a general X11/Wayland limit). Not tried here on a real session: only the real SDL clipboard under Xvfb (round trip) and the Lua side.

## 4. Tests (written first; all in `run_all.sh`)
`colour_test.lua` (hex <-> HSB: every grey, a million spread codes, 100k random, primaries, black, white, the middle, steps, clamping, greys keep their hue, invalid opens at the middle), `clipboard_test.lua` (copy, the answer, valid and refused texts), `clip_test.sh` (the C classifier: valid, empty, 64 and 65 characters, binary, 50 MB; the real SDL clipboard round trip under Xvfb), `menu_stress_test.lua` (the picker page in the random events with the invariants after every event, including "a preview never leaks after the picker closes" and "no file is written while it is open"; scripted checks of opening, steps, releases, repeat, Shift and Ctrl, rows, keep once, cancel by K2/Esc/F1, the middle, C, R, H and the entry, copy, every kind of paste, the entry's own copy/paste, the page's rows, shortcuts not taken, no clipboard binding), `rename_test.lua`, the updated `box_page_test.lua`, `ui_settings_test.lua`, `ui_keys_test.lua`, `textentry_test.lua` (the entry is reached through the picker), the real-window scenario `picker_scenario` (`probe_picker.lua`: opens, live colour in the window's pixels, no file while open, cancel, keep once), `box_c_test.sh` (every clipboard line of the shared files is inside `NORNS_LINUX_DESKTOP`; the aluminium golden hashes and the Mac build unchanged).

## 5. What differs from the plan, and what is not known
- The panel, strips, wheel/click mapping and their pictures are gone (decision of the owner). Floor and recent colours dropped.
- **K3 on the HEX row opens the text entry** (K3 on the other rows keeps): so Enter on HEX is not OK; move up first. `H` opens the entry from anywhere.
- OK without a move writes nothing (nothing to keep). Closing the menu (a short K1) with the picker open leaves it open, the preview stays; leaving by any page change restores.
- Text entry: Ctrl+C/V work in the picker's entry only (`opts.clip`); names and scripts' entries are unchanged.
- The pixel style's live preview uses the quick drawing; its smoothness on a real display is **not measured** (Xvfb only). Not measured here either: the real clipboard on the owner's session (X11 or Wayland), and the laptop keyboard (Shift/Ctrl combinations that a window manager may take).
- The hue of a grey opened first in a session is 180 (the middle), not a guess from the code.
