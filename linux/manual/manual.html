1. What this is

Verdandi Linux is the Linux version of Verdandi: the norns software (matron, crone with softcut, SuperCollider, maiden) running as an application on a desktop computer. From here on this manual says just “Verdandi”. It shows the device as a window, with its screen, three keys and three encoders (K1–K3, E1–E3) and a row of buttons above it. It can open a virtual grid, a virtual arc and a virtual keyboard, talks to real grids, arcs, crow and MIDI devices over USB, and uses JACK or PipeWire for sound.

It is not a Raspberry Pi: the operating system owns WiFi, updates and power (see section 12).

Tested: the automated tests run on Ubuntu 24.04 in a container without a sound card (a dummy JACK driver, fake sound cards, a virtual X server). The owner also ran it on Linux Mint 22.2 with PipeWire and reported results that led to the fixes described here. Anything that needs a real sound card, a real grid or arc, or a real browser session is listed in docs/port/HARDWARE-CHECKLIST.md.

2. Installing and building

Ubuntu 24.04 and derivatives with apt. Linux Mint 22 is Ubuntu 24.04 underneath; Debian and others are untested (package names may differ).

mkdir -p ~/verdandi-home
git clone -b linux-port <url of this repository> ~/verdandi-home/norns
cd ~/verdandi-home/norns
linux/setup-deps.sh     # needs sudo, read it first
linux/build.sh          # result: build/norns/norns
linux/tests/run_all.sh  # optional: the tests that need no hardware
  • linux/setup-deps.sh installs the build and run packages with apt (this uses sudo), builds libmonome 1.4.9 with this repository's patch (virtual grid and arc) into /usr/local, and installs waf 2.1.9 into ~/.local/share/waf (no sudo, owned by you). It does not need a python command, only python3.
  • It then builds maiden (the web editor and script catalog) as you, not as root, with linux/maiden-build.sh: the Go toolchain from apt, node 16.20.2 downloaded into a temporary folder (checksum checked, deleted afterwards), into ~/verdandi-home/maiden. This needs the network and a few minutes. NORNS_NO_MAIDEN=1 skips it. If it fails, the script prints a warning and everything else still works; run linux/maiden-build.sh again later.
  • linux/build.sh compiles norns with waf (desktop build) and builds two small tools, build/linux/audio_devices and build/linux/plugin_arch_check. If maiden is missing or its patches changed it builds maiden too.

The licenses of what is built are in docs/port/DEPS.md.

3. Starting it

cd ~/verdandi-home/norns
linux/norns.sh              # matron's log in ~/verdandi-home/logs/norns.log; maiden's norns console works
linux/norns.sh --terminal   # matron's Lua prompt and log in this terminal

The launcher uses the folder above the repository as the norns home (like /home/we on the device): dust/ (scripts, audio, data), matronrc.lua, the logs and audio.conf live there, and HOME is set to it while norns runs. Another folder: NORNS_HOME=/some/folder linux/norns.sh; it must contain norns (a link or the clone).

What the launcher does, in order:

  1. Chooses the audio server: a JACK server that already answers is used; otherwise, if PipeWire runs, the launcher starts itself again under pw-jack and says so; otherwise it starts its own jackd. See section 5.
  2. Creates dust/code, dust/audio, dust/data, matronrc.lua (the window as screen) and the SuperCollider configuration for the norns home, if they are missing.
  3. Runs the plug-in architecture check (section 8), then starts norns (matron, crone, softcut) and sclang.
  4. Starts maiden if it is built (section 7), and prints the address.

Starting it a second time (from the application menu, the verdandi command, or the launcher again) does not start a second copy: it asks the running Verdandi to bring its window to the front (restored if it was minimised, on its own desktop if your window manager allows it; the screen window too, if the screen is detached) and shows no dialog when that worked. Nothing of the running Verdandi is touched (its logs, settings and scripts stay as they are). If there is no window to bring (Verdandi still starting, running without a window, or an older build that does not answer), you get one dialog sentence saying why. On Wayland the desktop decides whether a window may jump to the front; it may only be marked in the panel. Close the window or press Ctrl+Q in it to quit; in the terminal Ctrl+C also stops it, and everything the launcher started stops with it, maiden included.

First run without sound: NORNS_JACK_DRIVER=dummy linux/norns.sh --terminal starts its own silent JACK server, so nothing depends on PipeWire.

--terminal and maiden's norns console exclude each other, see section 13.

4. The window

The window is the norns screen on a drawing of the device. It can be resized. Closing it ends norns.

Keyboard

While the window has the focus, and wherever nothing else wants the keys (in the menu, and in every script that does not read the keyboard itself):

keysnorns
1 2 3K1 K2 K3 (held while held)
Q / WE1 left / right
A / SE2 left / right (in scripts also ↑ / ↓)
Z / XE3 left / right (in scripts also ← / →)
Shift added5 steps at a time
F1–F4, F5the menu pages; F5 opens and closes the menu
F6 / F7 / F8the virtual grid / keyboard / arc windows
Ctrl+Mmute: the output off and back, from the box window and the screen window, with the row of page buttons shown or hidden. It is taken by Verdandi before a script sees it (verdandi scan-fkeys lists scripts that test keyboard.ctrl() and name the letter M)
F9, F11, Shift+F11the screen window: detach the screen or bring it back (F9, from any window), fullscreen on and off (F11, in the screen window), its title bar on and off (Shift+F11). A script that reads these keys itself does not get them on the Linux desktop (verdandi scan-fkeys lists which of yours name them)

Scripts that read the keyboard themselves (keyboard.code / keyboard.char) get the keyboard. For those, Alt plus the keys above always works as K and E, and Alt+Esc switches the hardware keys on or off by force. The automatic part is lua/core/keyboard.lua; the launcher sets NORNS_HARDWARE_KEYS=1 for it (it is off on the device).

Mouse

Click a key to press it. Drag a knob (up or right turns it clockwise) or scroll over it; the wheel elsewhere turns the nearest knob. There is no output slider on the window: the output level is on the MIX page (E2 changes it; with the mouse on the screen, the OUT column: drag or scroll over it, double-click for 0 dB) and under PARAMS > EDIT > LEVELS. The MUTE button, the last button of the row above the device, switches the output off and back; its light is on while muted. Ctrl+M and the menu item “Mute output” do the same; with the row of buttons hidden (below) a small MUTE button stays on the box while the output is muted, and clicking it unmutes. On the MIX page the mouse works on the screen itself.

The buttons above the device

These are not on the hardware. MIX, TAPE, HOME and PARAMS open the menu pages (clicking the page that is up goes back to the script). MIC goes through the audio inputs (see section 5). GRID, ARC and KEYS open the virtual windows. MAIDEN opens the maiden page in your browser; if nothing answers on maiden's port the window shows a note ("maiden is not running, see log") instead, and if the page opens but there is no norns console (the --terminal case) the note says so. MANUAL opens this page; if the file is missing the window says "manual not found: linux/manual/manual.html". MUTE (right end of the row) switches the sound output off and on again; it keeps the level you had and gives it back, and its light shows that the output is muted.

SYSTEM > SCREEN: brightness, colour, contrast

HOME > SYSTEM > SCREEN (below AUDIO; it was called UI in earlier versions) sets how the screen looks in the window. E2 chooses the row, E3 (or the mouse wheel over it) changes the value, K2 goes back. A change shows at once and is kept for the next start.

rowvaluesdoes
BRIGHTNESS0.1 to 1 in steps of 0.1, default 1dims the whole screen; the low steps are lifted a little so that 0.1 is dim but still readable
COLOURWHITE, YELLOW, PINK, CUSTOMthe colour of the lit pixels (black stays black); CUSTOM shows once a colour has been entered
CONTRAST0 to 1 in steps of 0.1, default 0.5lifts the dim grey levels: the levels many scripts use for waveforms and labels are nearly black on a computer screen, CONTRAST makes them lighter (higher number = lighter dim greys; 0 is the plain, linear mapping of the first versions, 1 the strongest lift). It changes how every script looks and how screenshots and GIFs look: they match the window, not exactly a norns
HEXany colourK3 opens the colour picker: the screen shows the colour you are choosing while it is open; K3 keeps it, K2 gives the old one back. Ctrl+C on this row copies the code, Ctrl+V pastes one and keeps it. A very dark colour is raised to full value so that it cannot hide the screen

The settings are in ui.conf in the norns home (brightness=, colour=, custom=, contrast=, file_dialog=); it can be edited by hand (an old file with greys= is still read and converted). A missing file means white, brightness 1, contrast 0.5; a bad value falls back to its own default with a line in logs/norns.log; unknown keys are ignored. The recording of a script's own PNG (screen.export_png) is not changed by these settings.

SYSTEM > THEME: the look of the box

HOME > SYSTEM > THEME (below SCREEN; it was called BOX in earlier versions) sets how the box looks: a style, five colours, and looks of your own. E2 chooses the row, E3 changes the value, K3 opens or acts, K2 goes back. A change shows at once and is kept for the next start. The page has six rows on the screen and scrolls.

rowdoes
STYLEALUMINIUM (the default: the brushed aluminium box as before) or PIXEL (hard-edged blocks, matt, a pixel font; keys are big rounded squares). STYLE changes only the style: the five colours stay as they are, so any look can be worn on either style.
PIXEL LOOKonly while STYLE is PIXEL (otherwise the row is dim and says “needs STYLE PIXEL”): PIXEL (the look described above, never changed), RETRO (chunkier 4-unit blocks, hard outlines, drop shadows on buttons and keys, stepped round encoders with a pixel highlight, a calm dithered band at the top and bottom of the box, a very faint speckle and a small grille), 8-BIT (the same chunky blocks, plain: no speckle, no grille, no text shadow) or 16-BIT (finer 3-unit blocks with more shading by dither: keys and encoders are shaded with a dither pattern, a faint scanline hint). E3 steps through them, K3 goes to the next one and round. It is independent of PRESET and of the colours: every look works with every colour, the built-in looks and your own, and the colour picker changes them live in every look. The box in RETRO and 8-BIT is 2 units taller than in PIXEL and the buttons are 72 units wide; their hit areas follow the drawing. The labels on the buttons keep their small size (they cannot be as chunky as the blocks).
PRESETthe look in use. E3 steps through the looks; K3 opens the list: the built-in looks DARK, LIGHT, COLOUR and MAC (the colours of the Mac app’s box), then, after “- MY PRESETS -”, your own, each marked with a *. A look is the five colours: choosing one sets the colours and never the style (use STYLE for that). NAME~ means the colours were changed since; CUSTOM means no look.
BOX, KEYS, ENCODERS, BUTTONS, FONTthe five colours, for whichever style is selected. K3 opens the colour picker (the same as SCREEN’s HEX row): the box, keys, encoders, buttons or font change live while it is open, K3 keeps the colour, K2 gives the old one back. Ctrl+C on a colour row copies its code, Ctrl+V pastes a code and keeps it. A hard-to-read pair of FONT and BUTTONS is accepted with a warning. Changing one colour never changes the style. In the aluminium style the colours tint the brushed metal; a part left at its default is drawn exactly as before.
SAVEK3 asks for a name and keeps the five colours as a look of your own (the style is not part of it) (1 to 18 letters, digits, spaces, - _ .; no path characters; not a built-in name). A name that exists asks “OVERWRITE …?” first. Each look is one small file, box-presets/<name>.box in the norns home, so it can be copied to another computer; a damaged file is ignored with a line in logs/norns.log. Up to 64.
DELETEonly while one of your own looks is in use. K3 asks once. The colours stay on the box and the look reads CUSTOM. The built-in looks can never be changed or deleted.

The settings are in box.conf in the norns home (style=, pixel_look= (pixel, retro, 8-bit or 16-bit), preset=, box=, keys=, encoders=, buttons=, font=, show_buttons=); it can be edited by hand. A missing file means the aluminium style with its own colours; a bad value falls back to its default with a line in logs/norns.log. The pixel style uses the screen’s font (resources/norns.ttf) for the button labels, and a built-in small font if that file is not found.

The colour picker

It opens when you press K3 (or Enter, or the right arrow) on a colour row of THEME (BOX, KEYS, ENCODERS, BUTTONS, FONT) or on SCREEN’s HEX row, and it is a page of the norns screen like any other: rows HUE, SATURATION, BRIGHTNESS and HEX, each with a small bar and its value. Every change shows at once on the box (or the screen) and nothing is written until you keep it.

keydoes
Up / Down, E2choose the row
Left / Right, - / =, E3change the row by a step: 5 degrees of hue, 5 percent of saturation or brightness. Shift makes it five steps, Ctrl a fine step of 1. Holding a value key repeats it; letting go changes nothing. The mouse wheel over E3 works too. The values stop at both ends
PageUp / PageDown, Home / Endfive steps; the smallest and the largest value of the row
K3 (Enter)keep the colour and save it: the page you came from says “saved #3B6EA8” until the next key (on the HEX row K3 opens the text entry instead). The picker’s last line reminds you: K3 keeps, K2 cancels
K2 (Esc)give the old colour back; the page says “restored”
F1 to F4, any other way outa change you had not kept is given back and the box shows “restored, not saved” for a few seconds
on the HEX row: Left / Right, - / =, E3make the code lighter or darker (the brightness) by the same steps, without opening the text entry
Htype a code in the text entry (3 or 6 digits, with or without #); the rows follow what you typed
Ccentre: hue 180, saturation 50, brightness 50 (#408080)
Rback to the colour the picker opened with
Ctrl+C / Ctrl+Vcopy the code (#3B6EA8) to the system clipboard; paste one. A pasted code can have 3 or 6 digits, with or without #. Anything else (text, an empty or very long clipboard, a binary one) is refused with a short message and nothing changes

Opening on a colour that is set puts the rows where that colour is, so nothing changes until you move one. With no colour yet (the SCREEN HEX row before you entered one) the rows start at the middle. A grey, white or black has no hue: the picker keeps the last hue it had, so raising the saturation again does not jump. In the text entry the arrows move through the characters (left and right choose a character, up and down switch between the characters and DEL / OK) and Ctrl+C / Ctrl+V copy and paste the code.

The clipboard is the system one: it works with X11 and, in a Wayland session, while the window has the keyboard focus; the code stays on it after Verdandi is closed only if your desktop has a clipboard manager (a normal X11 or Wayland limit).

Hiding the row of buttons

The right-click item Show the page buttons (ticked by default) hides or shows the row above the device, in both styles. Hidden, the buttons are not drawn and cannot be clicked, nothing else moves and the window keeps its size. Their keys keep working: F1–F4 open the pages, F5 the menu, F6–F8 the virtual windows; MAIDEN and MANUAL are menu items (“Open maiden”, “Open the manual”), and the input is in the menu as before.

The screen in its own window

F9 or the menu item “Screen in its own window” (in the right-click menu) pops the screen out into a second window called “Verdandi screen”: only the picture, live, with the brightness, colour and contrast of SYSTEM > SCREEN, and no box around it, but with the same black margin the box’s bezel has (4.30 percent of the picture’s width at each side, 7.29 percent of its height above and below), at every size and in fullscreen. Resize it as you like: when the picture at a whole multiple of 128 × 64 plus its margin is exactly the window (556 × 294 is 4×, 695 × 367 is 5×, 1112 × 587 is 8×; each multiple is 139 × 73.3 pixels) every screen pixel is a flat square; between those sizes the picture is enlarged to a whole multiple first and then scaled, so pixels stay as sharp as they can be, with black bars when the window is not that shape (a full-screen 1920 × 1080 is not an exact multiple, so it is in between). Screenshots and GIFs are the picture only, without the margin. F11 (or a double click) is fullscreen; Shift+F11 takes the title bar away (then drag the picture to move the window, and its edges to resize it).

While the screen is out, the main window keeps all its controls and shows a dark panel where the screen was: The screen is in its own window. Click here or press F9 to bring it back. Click it, press F9 (or use the menu item again), or close the screen window to bring the screen back. There is no button for this on the box. Closing the main window quits norns, with the screen window open or not. The keyboard works in the screen window exactly as in the main window (K1–K3, encoders, F1–F8, Ctrl+O, Ctrl+Shift+S, Ctrl+Q); F10 there brings the main window forward and opens its menu. The mouse over the picture does nothing (only the window itself: move, resize, fullscreen). Screenshots and GIFs are the same in both modes; their messages show in both windows. The virtual grid, arc and keyboard windows, real grids, arcs and MIDI devices are not affected by which window shows the screen.

Size, place, fullscreen, frame and whether the screen was out are remembered in screen-window.conf in the norns home (plain key=value lines, written by Verdandi: detached, x, y, w, h, fullscreen, border); a damaged value is replaced by its default with a line in logs/norns.log, and a saved place that is no longer on any display is forgotten. On Wayland the desktop may ignore the saved place.

5. Audio

Which audio server

norns talks JACK. Setting NORNS_AUDIO_SERVER: auto (the default) uses a JACK server that answers; if none does and PipeWire runs, the launcher starts itself again under pw-jack (needs pipewire-jack); otherwise it starts its own jackd. jackd always starts its own, pipewire always uses pw-jack. Giving NORNS_JACK_DRIVER (for example dummy, for silence) also means its own jackd. The line norns.sh: audio server: … says what was chosen. If PipeWire holds the sound card, the default alsa driver of its own jackd fails because the card is busy: use PipeWire through pw-jack, or the dummy driver.

Which sound card

Under PipeWire norns plays to the default sink and listens to the default source of the desktop, read when norns starts. To pin a card put out_ports= and/or in_ports= (the start of the client name pw-jack jack_lsp shows before the colon) in audio.conf in the norns home, or set NORNS_OUT_PORTS / NORNS_IN_PORTS (the environment wins). crone picks one card only (never ports of two cards, and never MIDI or sink-monitor ports). A name that matches nothing falls back to the default card and says so. If no card is found norns starts anyway, unconnected: the window shows “AUDIO: not connected, see SYSTEM > AUDIO”.

SYSTEM > AUDIO

Shows what is connected. Under PipeWire the rate is PipeWire's and cannot be changed here; BUFFER is an experimental request (PIPEWIRE_QUANTUM, which PipeWire may refuse). With its own jackd the page changes input and output devices, rate and period; they are kept in audio.conf (input, output, rate, period) and APPLY restarts norns.

The input: MIC, SYS, APP, OFF

The MIC button goes MIC → SYS → OFF; the right-click menu also lists single applications.

modewhat norns hears
MICthe capture ports of the card norns chose
SYSthe sound of every application except norns (each PipeWire stream appears as a JACK client named after the application). Applications that start later join by themselves. Streams of capture devices (monitor, capture names) are not taken as applications. norns' own output is never in SYS, so it cannot feed back. While SYS or APP is on, the applications keep playing directly and norns' input monitor is off.
APPone application from the right-click menu
OFFnothing is connected

An extra, off by default: “sink monitor” (everything the sound card plays, norns included, so it can feed back) appears only with sys_monitor=1 in audio.conf or NORNS_SYS_MONITOR=1; while it is on the window shows a warning. With MIC on and speakers, a script that plays its input can feed back acoustically: keep the volume low or use headphones. The choice is kept for the next start.

The clock

The internal clock reads JACK's frame time. Under PipeWire with WirePlumber that time's base can jump when applications are linked into norns; the clock follows backward jumps (fixed; tested with a fake graph and a PipeWire-like setup). A forward jump after the start is still accepted and can make something waiting on clock.sync fire in a burst once (section 13). NORNS_CLOCK_DEBUG=1 logs jumps of more than a second.

6. MIDI, grid, arc

  • USB devices: real MIDI devices, grids, arcs and crow are found through udev, as upstream. The tests use virtual ones; real grids and arcs need your hardware.
  • The virtual windows: GRID (64, 128 or 256 keys, switch under the window), ARC and KEYS. The virtual grid and arc are a pseudo-terminal that libmonome opens like a USB device (this is what the libmonome patch is for). KEYS is a MIDI device named “norns keys” that norns sees; where the ALSA sequencer is available it is also an ALSA MIDI port of that name that other programs can connect to.
  • MIDI clock and notes from a DAW: norns has a JACK MIDI input port Verdandi:midi_in (device “Verdandi JACK in”). Connect your DAW's MIDI output to it (under PipeWire a Midi-Bridge port) with pw-jack jack_connect or a patchbay, and set clock_source to midi in PARAMS > CLOCK. Tested with a JACK client playing 120 BPM clock, start, stop, continue and song position.
  • Optional auto-connect: midi_in_from= in audio.conf (or NORNS_MIDI_IN_FROM) lists the start of port names to link to Verdandi:midi_in, separated by ;, with * for a changing number (for example Midi-Bridge:Client-* Virtual RawMIDI). norns checks every 2 seconds and links again if a link is cut. Its own MIDI ports and Midi Through are never linked. Off without the line. SYSTEM > DEVICES > MIDI shows how many are linked.
  • serialosc and a real grid: if serialosc runs as a system service it opens the grid's serial port at the same time as norns, and two programs reading one stream make grid events lag or arrive wrong. norns checks for this when it opens a grid or arc and every 3 seconds, and only tells you: one line in the log with the commands (sudo systemctl stop serialosc.service, replug the grid), and the note “GRID: serialosc has this grid, see log” on the window until it is gone. It stops nothing. NORNS_SERIALOSC_CHECK=0 or serialosc_check=0 turns it off. norns does not use serialosc's OSC route.

7. maiden and the script catalog

maiden is the web editor of norns: a file tree of dust, an editor, the consoles (matron and SuperCollider) and the script catalog (install and update). When it is built, the launcher starts it and prints maiden at http://127.0.0.1:5000/maiden. The MAIDEN button opens that page. The log is logs/maiden.log in the norns home.

  • Port: 5000, or NORNS_MAIDEN_PORT=5001 linux/norns.sh. If the port is taken the launcher says so and does not start maiden. The consoles use fixed ports: 5555 (norns) and 5556 (SuperCollider).
  • Where things go: installed scripts into dust/code/<name>/, the catalogs into dust/data/catalogs, the sources they come from into dust/data/sources (copied on the first start). The editor reads and writes anything under dust and nothing outside it. A script is installed by downloading it (git or zip); maiden runs nothing while installing.
  • Safety: maiden and both consoles answer on 127.0.0.1 only, so other computers cannot reach them (tested). In addition, a web page from another site open in your browser cannot use them: the consoles keep a browser connection only if its page came from maiden's own address (127.0.0.1 or localhost with maiden's port), and maiden refuses requests with another Host or Origin. Programs on your own computer, such as maiden-repl and your scripts, are not affected: they can do what you can. The consoles run code (Lua, SuperCollider) as you, as on the device.
  • The units commands of maiden (;restart and the like, which talk to systemd on a norns) are switched off here and answer “not available in Verdandi”. Restart norns from its window (SYSTEM > RESTART) or start it again.
  • The norns console needs a start without --terminal. See section 13.

Checked by tests: the binds, the editor's file API, installing a script from a zip and running it in norns, the refusals above, the button. Checked once by hand over the network: installing a script from GitHub through maiden's git route, and downloading the catalog. The real browser session with the real catalog is for your computer (docs/port/HARDWARE-CHECKLIST.md).

8. Scripts

Scripts live in dust/code/<name>/<name>.lua. Put them there, import them from the right-click menu, or install them from maiden; choose one in HOME > SELECT.

Mods

As on the device, every folder dust/code/<name>/ that has lib/mod.lua is a mod and is listed in HOME > SYSTEM > MODS (E3 right enables it, left disables it; the choice is kept in dust/data/system.mods). Enabled mods are loaded when norns starts, so enable, then restart norns (SYSTEM > RESTART). logs/norns.log has one line for every mod found (“mod found: name …”, enabled or not), one for every mod loaded and, if a mod has an error, “mod failed: name: …” with the error; the other mods still load and norns goes on. Mods that need a SuperCollider extension (an nb voice such as doubledecker has a .sc file) are compiled with the rest of dust when SuperCollider starts.

/home/we

Scripts see the device's paths: os.getenv('HOME') and _path say /home/we, and norns translates such paths to the norns home wherever they leave Lua (files, shell commands, require, softcut, SuperCollider, the sidecar). Output coming back is translated the other way. Scripts and libraries are named with the virtual path (debug.getinfo(1).source is @/home/we/dust/code/…), so libraries that find their own folder with it work (nb, used by Cheat Codes 2, is tested). Error messages and tracebacks therefore show /home/we/…, as on the device; the real home is printed once at the top of the log (virtual /home/we -> …).

/home/we inside SuperCollider

Engines are written in SuperCollider, which has no idea of the virtual /home/we. The launcher therefore loads a small class folder (sc/linux) that maps /home/we to the norns home in SuperCollider's file, sound file, shell and server-message functions (PathName, File, Buffer.read, .load, unixCmd …). This is why scripts such as dronecaster and bloom, whose engines read their sample folders by the device path, make sound here. logs/sclang.log shows about two dozen “Extension … overwrites” lines at start; they are these overrides and harmless. The next start after an update rewrites sclang_conf.yaml (the old one is kept as sclang_conf.yaml.old). To list the scripts that depend on it: python3 linux/scan-sc-paths.py ~/Verdandi/dust/code. Plug-in code inside scsynth that opens files by itself is not covered (none is known).

Commands scripts run

norns and the commands its scripts run (os.execute, norns.system_cmd) get linux/shims first on their PATH. sudo systemctl restart norns-… (a script's installer asks for this on a Raspberry Pi) returns at once with exit 0, prints norns: there is no systemd for norns on this build … and norns restarts itself within a few seconds. Other sudo commands run as sudo -n: if a password would be needed they fail at once instead of freezing norns. NORNS_NO_SHIMS=1 switches this off. A script that calls /usr/bin/sudo by its full path is not covered. wget, apt and apt-get are not provided.

The answer a script reads from a command (os.capture, io.popen, norns.system_cmd) is what the command writes to its standard output, as on the device; the complaints it writes to standard error go to logs/norns.log. A script that lists a folder that does not exist therefore gets an empty answer (this is what makes mx.samples offer “get?” for a pack that is not downloaded). A command that says 2>&1 itself still gets its errors, and starting norns with NORNS_CAPTURE_STDERR=1 merges them for every command. /home/we in a command is the norns home (see above); the text of a shell script that a command runs is not rewritten, so a script file that names /home/we inside itself needs the real folder. Downloads like mx.samples’ need curl and unzip; the package recommends both.

Plug-ins built for another machine

A script's installer may download SuperCollider plug-ins built for the Raspberry Pi (32-bit ARM .so files, for example PortedPlugins-RaspberryPi.zip). They cannot load on a PC, and SuperCollider stops at the first plug-in it cannot load: no engines, “SUPERCOLLIDER FAIL”, wrong ELF class in logs/sclang.log. Before SuperCollider starts, norns reads the header of every plug-in in ~/verdandi-home/.local/share/SuperCollider/Extensions, /usr/local/share/SuperCollider/Extensions, /usr/share/SuperCollider/Extensions and (*_scsynth.so and .scx only) dust/code, and compares it with this machine. For each folder with wrong files it prints one line: the folder, the bad files and what they are, why SuperCollider will fail, one command (verdandi tidy disable) that moves them to ~/verdandi-home/disabled/ with a manifest line so they can be restored (also SYSTEM > CLEAN UP). It never moves or deletes anything; the window shows “PLUGINS: wrong-architecture plug-in, see log” until no wrong file is left (re-checked every 3 seconds). After moving the files, restart norns. NORNS_PLUGIN_CHECK=0 or plugin_check=0 in audio.conf turns the check off.

12. Differences from the device

  • No hardware: the OLED is a window, the keys and encoders are the keyboard and mouse. The SYSTEM menu has DEVICES, AUDIO, MODS, SCREEN, THEME, CLEAN UP, RESET and RESTART: WIFI, UPDATE, the password and the display settings are not offered, because the operating system owns them. SLEEP (HOME page) quits norns without powering off the computer; RESTART restarts norns through the launcher.
  • Update scripts in maiden, and Verdandi itself by getting a new version of the repository.
  • Everything that listens (maiden, the consoles) is on 127.0.0.1 only, unlike the device.
  • No AppImage or Flatpak package yet, and no plug-in version (VST3 is planned for the Windows version).
  • Compared with the Mac version: the same window code, skins and import logic; the audio server (JACK or PipeWire instead of Core Audio), the input taps (PipeWire clients instead of Core Audio process taps), the file dialogs, the screenshot folder and the menu (drawn in the window, there is no menu bar) are Linux specific; there is no AUv3.

13. Known limitations

Scripts with prebuilt Raspberry Pi plug-ins

Scripts whose installer downloads ARM plug-ins (about 71 of the 351 community scripts of the catalog scan in macos/docs/02-katalog-scan.md need prebuilt SuperCollider plug-ins) cannot use them: they are 32-bit ARM and this computer is not. norns reports them (section 8) and moves nothing, but SuperCollider does not start while one is in a place it reads. There is no x86_64 build of those bundles here. Installing such a script through maiden works; running its engine does not, until the plug-ins are out of the way (and then only the engines that do not need them).

Raspberry Pi system commands

Only sudo systemctl … norns-… is answered (as a restart of norns). Other sudo commands run with sudo -n and fail if a password is needed; wget, apt and apt-get are not provided; scripts that call full paths such as /usr/bin/sudo, or that expect Raspberry Pi tools and files, will fail or do nothing.

--terminal and maiden's norns console

matron's Lua prompt is one text stream. With --terminal it is your terminal; without it ws-wrapper offers it on ws://127.0.0.1:5555, which is what maiden's console and maiden-repl connect to. It cannot be both, so with --terminal nothing listens on 5555, the maiden page says “not connected to norns” (the SuperCollider console and the rest of maiden work), and the launcher and the MAIDEN button say so. To have a terminal prompt as well, start linux/norns.sh without --terminal and run build/maiden-repl/maiden-repl in a second terminal (it connects to the same sockets; not tested against a running norns).

serialosc and a real grid

A serialosc service that holds the grid's serial port makes grid events unreliable. norns detects this and warns (section 6) but does not stop serialosc, and does not use serialosc's OSC route.

SynthDefs that SuperCollider 3.14 rejects

Verdandi ships SuperCollider 3.14.1, which refuses a few things that 3.13 let through. The one known case is mx_malone of the mod nb_mxsynths (“Clip first input is not audio rate”); without a fix the mod would stop creating its other voices. Verdandi lets that one SynthDef build (a small extension in sc/linux-compat, one line in logs/sclang.log, none of your files is changed). A new case shows as SynthDef … build failed in logs/sclang.log; the name can be added with NORNS_SYNTHDEF_COMPAT=name when starting, and the cause is in the mod (a patch for its author is in docs/port/synthdef-3.14/; KNOWN-ISSUES item 21).

Other open points

  • The internal clock: a forward jump of JACK's frame time after the start is accepted as it is and can make waiting coroutines fire once in a burst. A handling is proposed in docs/port/clock-forward-jump-proposal.diff, not applied.
  • SYS is a set of links made by norns; unlinking an application that you want to hear only directly is not built.
  • PARAMS > CLOCK does not refresh the tempo by itself with an external clock (as on the device software, upstream behavior).
  • Not tested here at all: a real sound card in many setups, a real grid, arc or crow, Wayland and X11 differences, other distributions, the maiden page in other browsers than Chromium (the cross-site protection was exercised with Chromium only), and macOS after the shared-file changes.
